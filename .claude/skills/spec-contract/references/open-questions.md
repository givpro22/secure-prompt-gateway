## Q1. Case A의 규칙 매칭 건수 — 2건인가 3건인가

**충돌:** 기획서 세 곳이 갈린다.

| 위치 | 기술 |
|---|---|
| 10.4 데모 케이스표 | "BLOCK (SEC-DBURL-02, PII-RRN-01, SEC-PRIVIP-03)" — **3건** |
| 8.4 BLOCK 응답 예시 | `matches`에 SEC-DBURL-02, PII-RRN-01 — **2건** |
| 15.2 데모 스크립트 | "S4 BLOCK, 규칙 2건" — **2건** |

**원인:** Case A 입력의 `postgres://admin:p%40ss@10.0.3.21/prod`에서 사설 IP `10.0.3.21`이 DB URL 매칭 구간 **안에** 있다. SEC-DBURL-02(`[^\s]+`)가 공백 전까지 통째로 먹으므로 SEC-PRIVIP-03의 매칭 구간이 완전히 포함된다.

**권고: 2건.** 포함 관계인 매칭은 별도 finding으로 만들지 않는다(중첩 span 억제).

근거는 셋이다. 첫째, 기획서 두 곳(8.4·15.2)이 2건이고 10.4만 3건이므로 다수결이 아니라 **발표에서 실제로 읽히는 문서**가 2건이다. 둘째, 같은 문자열을 두 규칙이 이중으로 세면 감사 화면의 "규칙 N건"이 실제 위험 개수를 과장한다. 셋째, Case A는 BLOCK이라 `submitted_text`가 NULL이므로 억제된 IP가 마스킹되지 않아도 유출 위험이 없다.

**구현:** `ConflictResolver`에서 매칭을 span 시작 오프셋 순으로 정렬한 뒤, 이전 매칭의 span에 완전히 포함되는 매칭은 finding을 생성하지 않는다. 부분 겹침(포함 아님)은 억제하지 않고 7.6의 severity 규칙을 적용한다.

**후속:** `spec-steward`가 기획서 10.4를 2건으로 수정한다. 문서를 안 고치면 발표 중 누군가 3건이라고 말한다.

**결정 안 하면:** 데모 0:00 화면에 "규칙 3건"이 뜨고 발표자는 "2건"이라고 말한다. 첫 번째 케이스에서 바로 드러난다.

## Q2. 정보보안팀의 부서 코드

**충돌:** 10.2가 "정보보안팀은 department에 추가하되 정책 매핑은 없음"이라 지시하지만, 7.3 부서별 적용 매트릭스에는 DEV·SALES·HR 3개만 있고 코드가 정의되지 않았다. 5.4 감사 콘솔 부서 필터 옵션도 "전체, 개발팀, 영업팀, 인사팀"이다.

**권고:** code `INFOSEC`, name `정보보안팀`. `P-SEC` 정책 코드와 헷갈리므로 `SEC`는 쓰지 않는다.

부서 필터 드롭다운에는 **추가하지 않는다.** 박OO(SECURITY_ADMIN)는 프롬프트를 제출하지 않으므로 이 부서의 inspection이 0건이고, 항상 빈 결과를 내는 필터 옵션은 데모에서 오히려 해가 된다.

**결정 안 하면:** `app_user`의 박OO에 넣을 `dept_id`가 없어 시드 SQL이 FK 제약으로 실패한다. `data-architect`가 여기서 막힌다.

## Q3. span 재계산 책임 — BE인가 FE인가

**배경:** 7.6이 "span은 원문 기준 오프셋으로 finding에 저장. 화면 하이라이트는 submitted_text 기준으로 재계산"이라고만 하고 주체를 정하지 않았다. 마스킹은 길이를 바꾸므로(`900101-1234567` 14자 → `[주민번호]` 6자) 두 좌표계가 어긋난다.

**권고: 오프셋 산술을 아예 하지 않는다.** FE는 `submittedText`에서 `mask_label` 문자열(`[주민번호]`, `[전화번호]`, `[카드번호]`, `[이메일]`, `[내부IP]`)을 찾아 `<mark>`로 감싼다. 라벨은 대괄호로 시작하는 고유 형태라 오탐이 사실상 없다.

이유는 재계산 로직이 3일 프로젝트에서 감당할 만한 이득이 없기 때문이다. 다중 매칭·중첩·길이 변화가 겹치면 누적 델타 계산이 필요하고, 틀리면 하이라이트가 조용히 밀린다. 라벨 검색은 틀릴 여지가 없고 코드가 세 줄이다.

**대안(라벨이 겹치는 경우):** 같은 라벨이 여러 번 나오면 전부 하이라이트한다. 어느 것이 어느 규칙인지 구분할 필요는 화면 요구사항에 없다(5.3은 "마스킹 구간 하이라이트"까지만 요구).

**DB 저장은 그대로 원문 기준.** 감사 목적상 원문 어디였는지가 증적이므로 바꾸지 않는다.

**결정 안 하면:** FE가 원문 기준 span을 마스킹본에 그대로 적용해 엉뚱한 글자에 하이라이트가 걸린다. `integration-qa`가 잡기 전까지 아무도 모른다.

## Q4. 201 Created를 쓰지 않는 것

**배경:** 8.2 상태 코드 정책에 201이 정의되어 있으나 "판정 결과에 따라 200/202/403으로 갈림"이라고 적혀 있고, 8.3 엔드포인트 목록의 `POST /messages` 상태 칸에도 201이 없다. 즉 정의만 있고 사용처가 없다.

**권고: 201을 쓰지 않고, 쓰지 않는 이유를 발표 자료에 남긴다.**

`POST /messages`는 message 리소스를 실제로 생성하지만, 클라이언트가 받아야 할 주 정보는 생성 사실이 아니라 **판정 결과**다. 201 + Location으로 응답하면 FE가 판정을 알기 위해 한 번 더 요청해야 하고, BLOCK을 201로 표현할 방법도 없다. 그래서 판정 결과를 본문에 실어 200/202/403으로 갈랐다.

이것은 누락이 아니라 설계 판단이며, 정량 루브릭이 "RESTful 규격(Method, Path, Status Code)"을 평가하므로 **근거를 말할 수 있으면 오히려 가점 요인**이다. 예상 질의(16장)에 항목을 추가해 둔다.

**결정 안 하면:** Q&A에서 "왜 POST인데 201이 없나"를 받고 즉석에서 답을 만들게 된다.

## Q5. 겹치는 span에서 BLOCK 규칙이 이길 때의 마스킹 라벨

**배경:** 7.6은 "같은 구간에 두 규칙이 겹치면 severity 높은 규칙의 라벨 사용"이라 하는데, BLOCK 액션 규칙(SEC-DBURL-02, SEC-AWSKEY-01)에는 `mask_label`이 없다(`—`).

**권고: Q1의 중첩 억제로 해소된다.** 포함 관계면 안쪽 매칭 자체를 만들지 않으므로 라벨 충돌이 발생하지 않는다.

부분 겹침에서 BLOCK과 MASK가 만나는 경우는 더 근본적으로 문제가 되지 않는다. BLOCK이 하나라도 있으면 최종 판정이 BLOCK이고 `submitted_text`가 NULL이라 마스킹 자체를 수행하지 않기 때문이다(7.5). **마스킹은 최종 판정이 MASK 또는 PENDING일 때만 실행한다.**

**구현 순서를 이렇게 고정한다:** 매칭 수집 → 중첩 억제 → 충돌 해결로 최종 판정 결정 → **판정이 BLOCK이 아닐 때만** 마스킹 실행.

**결정 안 하면:** BLOCK 케이스에서 Masker가 `mask_label`이 null인 규칙을 만나 NPE를 던진다. Case A가 데모 첫 케이스다.

## Q6. `review_status`에 CONFIRMED가 포함되는가

**충돌:** 6.2 `inspection_finding` 테이블 설명의 값 나열은 "SUGGESTED, ACCEPTED, REJECTED"인데, 같은 줄 뒤에 "규칙 finding은 CONFIRMED 고정"이라고 적혀 있다. 8.4 `GET /inspections/{id}` 응답 예시에도 규칙 finding이 `"reviewStatus": "CONFIRMED"`로 나온다.

**권고: enum은 4개다.** `SUGGESTED, ACCEPTED, REJECTED, CONFIRMED`. DB CHECK 제약과 FE 분기 모두 4개 값을 다룬다.

의미는 이렇게 고정한다. `CONFIRMED`는 규칙 엔진이 확정한 상태로 사람의 검토 대상이 아니다(ACCEPT/REJECT 버튼 미노출). `SUGGESTED`만 검토 대상이다. 이 구분이 5.4 상세 패널에서 "규칙 판정(결정)"과 "AI 제안(후보)"을 좌우로 나누는 근거다.

**결정 안 하면:** DB CHECK 제약에 CONFIRMED가 빠져 규칙 finding INSERT가 실패하거나, FE가 CONFIRMED를 모르는 값으로 처리해 규칙 판정에도 ACCEPT/REJECT 버튼이 뜬다. 후자는 "AI만 사람이 확정한다"는 책임 경계 주장과 정면으로 어긋나 발표에서 지적당한다.
