# 홍보팀 엠바고 데모 — 착수 전 영향 분석

작성 2026-09-02. 내일 작업 순서를 잡기 위한 사전 조사였다.

> **2026-09-02 결정 완료.** 네 결정이 모두 확정되어 구현·반영되었다 — 1은 A안(프론트 텍스트 추출),
> 2는 홍보팀 신설, 3은 **B안(`policy.owner_dept_id` 컬럼 추가)**, 4는 B안(`policy_rule.embargo_until`)

## 2. 규칙 하나를 추가하면 같이 고쳐야 하는 곳 — 6군데

규칙은 DB에만 있는 게 아니다. 같은 정의가 6곳에 흩어져 있다.

1. `V3__*.sql` (신규 마이그레이션)
2. `frontend/dev/fixture-server.js`의 `RULES` 배열 — 정규식을 JS로 다시 씀
3. 기획서 7.2 규칙표 — 발표 자료에 그대로 실린다
4. `docs/api-spec.md` 예시 응답
5. `_workspace/01_api-ai-architect_contract-freeze.md` (계약 확정본)
6. 테스트 기대값

**하나라도 빠지면 픽스처 모드와 실서버가 다른 판정을 낸다.** 내일 작업의 실제 비용은 규칙을 짜는 게 아니라 이 6곳 동기화다.

## 3. 막히는 지점 4개 — 결정이 필요하다

### 3-1. 파일·첨부는 명시적으로 범위 밖이다

기획서 0.3이 못 박았다.

> 검사 범위 — 만드는 것: 입력 프롬프트 / 만들지 않는 것: 출력 응답, **첨부파일**
> API — 만들지 않는 것: 정책 생성·수정, **첨부 업로드**

`attachment` 테이블은 Future 4개 중 하나로 DDL도 만들지 않았다 (`docs/erd.dbml`에 논리 모델로만 존재).

선택지:

| 안 | 방식 | 비용 | 범위 위반 |
|---|---|---|---|
| **A** | 프론트에서 xlsx/csv를 읽어 **텍스트로 추출한 뒤 기존 프롬프트 경로**로 전송. 화면에만 "파일 첨부" UI | 낮음. 백엔드·엔진 무변경 | 없음. 입력 프롬프트 검사 그대로 |
| B | `attachment` 테이블 + 추출기 어댑터 실구현 | 높음. 마이그레이션·엔티티·API 추가 | 0.3 위반. 기획서 수정 동반 |

**A안 권장.** 데모에서 보여줄 장면("엑셀 넣었더니 차단됨")은 A안으로 100% 같고, 기획서 17장 "향후 확장 4 — 첨부파일 검사, 엔진 무변경"과도 말이 맞는다. 발표에서 "추출기만 어댑터로 갈아끼우면 된다"는 설명이 그대로 성립한다.

### 3-2. 홍보팀이 없다

현재 부서는 DEV·SALES·HR·INFOSEC 4개. `department.code`에 CHECK 제약이 **없으므로** 추가는 INSERT 한 줄이다 (`(5, 'PR', '홍보팀')`). 사용자도 1명 추가해야 계정 드롭다운에 뜬다.

주의: 감사 로그 100건 시드는 dept 1~3만 쓴다. 홍보팀을 넣어도 기존 로그에는 안 나온다. 감사 콘솔 부서 필터에서 홍보팀을 고르면 0건이다 — 데모 중 눌러볼 수 있으니 홍보팀 로그 몇 건을 V3에서 같이 넣는 편이 낫다.

### 3-3. "홍보팀 정책"의 소유 개념이 스키마에 없다

`policy` 테이블에 소유 부서 컬럼이 없다. 있는 건 `scope`(GLOBAL/DEPT)와 `department_policy` 매핑뿐인데, 이 매핑의 의미는 **"이 정책이 적용되는 부서"**이지 "이 정책을 만든 부서"가 아니다.

요청은 *홍보팀이 건 엠바고에 개발팀·영업팀이 걸린다*이므로, 두 개념이 갈린다.

| 안 | 방식 | 비용 |
|---|---|---|
| **A** | 소유는 정책 **이름·description**으로만 표현. `P-EMBARGO / 홍보팀 보도자료 엠바고`, scope=DEPT, 매핑은 DEV·SALES | 없음. INSERT만 |
| B | `policy.owner_dept_id` 컬럼 추가 | V3 ALTER + 엔티티 + 응답 필드 + 화면 |

**A안 권장.** 화면에 "적용 정책: P-EMBARGO v1"이 뜨고 규칙 `source`에 "홍보팀 공지 2026-09-01"이 들어가면 시연에서 소유 주체는 충분히 드러난다. B안은 3일 프로젝트에서 얻는 게 적다.

### 3-4. 엠바고 날짜를 담을 자리가 없다 — 이게 제일 큰 결정

"○월 ○일까지 공개 불가"의 날짜를 넣을 컬럼이 `policy_rule`에 없다. 있는 컬럼은 pattern·action·mask_label·severity·obligation·source·description뿐이다.

게다가 **화면까지 날짜가 도달하려면** `RuleResult.RuleMatch`(code·category·action·span·matchedKeyword·severity·obligation·source) 8필드에도 자리가 없다. `description`은 애초에 응답에 안 실린다.

| 안 | 방식 | 비용 | 시연 품질 |
|---|---|---|---|
| A | 날짜를 `source` 문자열에 섞음 — `"홍보팀 엠바고 2026-10-15"` | 0. 스키마·계약 무변경 | 결과창에 출처로만 뜸. "언제까지"가 부차적으로 보임 |
| **B** | `policy_rule.embargo_until DATE` 컬럼 + `RuleMatch.embargoUntil` 필드 추가 | V3 ALTER + 엔티티 1필드 + record 1필드 + 픽스처서버 + 계약서 | 결과창에 **"2026-10-15까지 공개 불가"** 전용 문구. 데모의 핵심 대사 |
| C | 날짜를 규칙 `pattern` 키워드로 (`"오메가 런칭,신제품 발표"`) 두고 문구는 하드코딩 | 0 | 하드코딩. 정책이 DB에 있다는 주장(11.3 Config Isolation)이 깨짐 |

**B안 권장.** 이 데모의 값어치가 "날짜까지 정책으로 관리된다"에 있고, C안은 기획서 11.3 주장과 정면으로 부딪힌다. 비용도 컬럼 1개 수준이다.

추가 결정: 엠바고가 **날짜가 지나면 자동 해제**되어야 하는가?
- 해제 O — 엔진에 `embargo_until >= today` 판정 분기 추가. 시연에서 "날짜 지난 규칙은 통과"까지 보여줄 수 있어 설득력이 크다
- 해제 X — 날짜는 표시용 문자열일 뿐. 구현 0

시연 대본상 **해제 O**가 훨씬 강하다. 규칙 2개(만료 전/만료 후)를 시드에 넣고 나란히 보여주면 그 자체가 장면이 된다.

## 4. 마스킹·탐지 규칙 최신화 — 현행 8종의 실제 결함

지금 규칙에서 손볼 곳이 실제로 있다.

| 규칙 | 현재 패턴 | 문제 |
|---|---|---|
| `PII-RRN-01` | `\d{6}-?[1-4]\d{6}` | 앞뒤 `\b`가 없다. 긴 숫자열(주문번호·계좌) 내부에서 오탐 |
| `PII-PHONE-03` | `01[016789]-?\d{3,4}-?\d{4}` | 역시 `\b` 없음. 카드번호 매칭 구간과 겹칠 수 있다 |
| `PII-CARD-02` | `\b(\d{4}-?){3}\d{4}\b` | 반복되는 캡처 그룹이라 캡처가 무의미하다. 픽스처 서버는 이미 `(?:`로 써 있다 — 매칭 결과는 같지만 두 곳의 패턴 문자열이 이미 어긋나 있다는 신호다 |
| `SEC-DBURL-02` | `(postgres\|mysql\|jdbc)[\w+]*://[^\s]+` | `[^\s]+` greedy. 공백 없는 긴 문장에서 뒤까지 삼킨다. Case A는 마침 공백이 있어 통과 |

**추가 후보** — 요즘 유출 경로 기준:
`SEC-TOKEN-04` GitHub PAT `ghp_[A-Za-z0-9]{36}` / `SEC-BEARER-05` JWT `eyJ[\w-]+\.[\w-]+\.[\w-]+` / `SEC-OPENAIKEY-06` `sk-[A-Za-z0-9]{20,}` / `PII-ACCOUNT-05` 계좌번호 / `PII-PASSPORT-06` 여권번호 `[MSRO]\d{8}`.

단 규칙을 늘릴수록 §2의 6곳 동기화 비용이 배로 든다. **엠바고 데모에 필요한 최소 + 결함 4건 수정**으로 끊는 것을 권한다.

## 5. 입력창·결과 확인창 다듬기 — 실제로 손댈 파일

- `MessageInput.vue` (74줄) — textarea + 전송 버튼뿐. 파일 첨부 UI를 넣는다면 여기. 값은 부모(ChatView)가 들고 있다 (BLOCK 시 원문 복원 때문)
- `VerdictCard.vue` (214줄) — 결과창. 엠바고 문구를 넣는다면 `isBlock` 힌트 문단 옆이나 규칙 행(`.rule`) 안
- `ChatView.vue` (349줄) — S1~S5 5상태 기계. 상태를 늘리지 말 것. 엠바고는 S4(차단)의 변주로 넣는 게 맞다

`lib/terms.js`에 한국어 용어표가 있다. 새 카테고리를 만들면 여기도 추가해야 화면에 코드명이 그대로 노출되지 않는다.

## 6. 카테고리 CHECK 제약 — 걸릴 수 있는 함정

```sql
CHECK (category IN ('PII', 'SECRET', 'CONFIDENTIAL'))
```

엠바고를 새 카테고리 `EMBARGO`로 두고 싶다면 **V3에서 CHECK 제약을 갈아야** 한다. `PolicyCategory` enum과 `lib/terms.js`도 함께. `CONFIDENTIAL`로 얹으면 변경 0이다.

시연 화면에 "기밀"이 아니라 "엠바고"라고 뜨는 편이 낫다면 새 카테고리가 맞다. 판단이 필요하다.
