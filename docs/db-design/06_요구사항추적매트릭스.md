# 06. 요구사항 추적 매트릭스 (RTM)

**목적:** 데이터 요구사항 하나가 **ERD → 스키마 → 마이그레이션 → 엔티티 → API/화면**까지
끊기지 않고 도달했는지 한 표로 확인한다.

**읽는 법:** 어느 칸이든 비면 그 요구사항은 설계만 되고 구현되지 않았다는 뜻이다.
Q&A에서 "그건 어디에 구현되어 있나요"에 이 표 한 줄로 답한다.

---

## 3. 역방향 추적 — 테이블이 어떤 요구사항에서 나왔는가

"이 테이블 왜 있나요"에 대한 답이다. **근거 없는 테이블이 하나도 없다.**

| 테이블 | 유래 DR | 없으면 무엇이 불가능한가 |
|---|---|---|
| `department` | DR-10(부서별 적용 정책), DR-18(로그인 없는 사용자 식별) | 부서별 정책 차등 적용 자체가 불가능 |
| `app_user` | DR-18(로그인 없는 사용자 식별), DR-06(사람의 확정 기록) | 제출자·확정자를 식별할 수 없다 |
| `policy` | DR-09(기준은 코드가 아니라 데이터), DR-11(소유 부서≠적용 부서), DR-15(정책 버전 시점 보존) | 규칙을 묶는 단위와 버전 축이 사라진다 |
| `policy_rule` | DR-09(기준은 코드가 아니라 데이터), DR-12(규칙의 유효기간), DR-13(규칙 코드가 공통 식별자), DR-14(마스킹 라벨은 MASK에만) | 판단 기준이 코드로 되돌아간다 |
| `department_policy` | DR-10(부서별 적용 정책) | 데모 Case B/C(부서로 갈리는 판정)가 성립하지 않는다 |
| `message` | DR-01(원문/전송본 분리), DR-18(로그인 없는 사용자 식별) | 감사 증적의 원문이 남지 않는다 |
| `inspection` | DR-02(검사 1회=1레코드), DR-07(비동기 AI 상태 추적), DR-15(정책 버전 시점 보존), DR-19(스키마 변경 없이 AI 응답 보관) | 비동기 상태와 시점 스냅샷을 둘 곳이 없다 |
| `inspection_finding` | DR-03(근거를 항목 단위로)~06, DR-17(span은 원문 기준) | "왜 차단됐는가"를 설명할 수 없다 |

## 4. 화면·API 역방향 — 무엇이 무엇을 읽는가

| 화면/API | 읽는 테이블 | 핵심 컬럼 |
|---|---|---|
| SCR-01 정책 패널 · `GET /policies?deptId=` | `policy` `policy_rule` `department_policy` | `scope`, `embargo_until` |
| SCR-01 제출 · `POST /messages` | `policy_rule`(읽기) → `message` `inspection` `inspection_finding`(쓰기) | `pattern`, `action`, `submitted_text` |
| SCR-01 폴링 · `GET /inspections/{id}` | `inspection` `inspection_finding` | `ai_status`, `findings[]` |
| SCR-02 목록 · `GET /inspections?...` | `inspection` ⋈ `message` ⋈ `app_user` ⋈ `department` | 인덱스 6개가 이 조인을 받는다 |
| SCR-02 확정 · `PATCH .../findings/{id}` | `inspection_finding` | `review_status`, `reviewed_by`, `reviewed_at` |
| 계정 전환 · `GET /users?deptId=` | `app_user` `department` | `X-User-Id`의 원천 |
