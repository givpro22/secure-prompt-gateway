# 04. 마이그레이션 설계서 (Flyway)

**입력:** [03 스키마 설계서](03_스키마설계서.md)
**출력:** `backend/src/main/resources/db/migration/V1__schema.sql` · `V2__seed.sql` · `V3__embargo.sql`
**도구:** Flyway (Spring Boot 3.5.3 자동 실행, `flyway-core` + `flyway-database-postgresql`)

---

## 1. 왜 Flyway인가 — `ddl-auto: update`를 쓰지 않는 이유

| 방식 | 문제 |
|---|---|
| `spring.jpa.hibernate.ddl-auto: update` | 엔티티에서 DDL을 **역산**한다. 컬럼 삭제·타입 변경을 하지 않고, CHECK 제약·코멘트·인덱스를 만들지 않는다. 03번 설계의 대부분이 사라진다 |
| 수동 SQL 실행 | 팀원 4명의 로컬 DB 상태가 각자 다르다. "내 컴퓨터에서는 되는데"의 표준 발생 경로 |
| **Flyway** ✅ | SQL이 곧 소스다. 적용 이력이 `flyway_schema_history`에 남고, 빈 DB에서 항상 같은 결과가 나온다 |

설정은 세 줄이다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate     # ← 만들지 않는다. 대조만 한다
  flyway:
    enabled: true
    locations: classpath:db/migration
```

**`validate`가 이 설계의 안전장치다.** 엔티티와 DDL이 컬럼 단위로 어긋나면 애플리케이션이
기동조차 하지 못한다. 사람이 대조표를 만들 필요가 없다 (05번 §5).

## 2. 파일 분할 — 03번이 넘긴 Q1

**스키마와 시드를 나눈다.** V1(DDL) / V2(데이터)

| 근거 | 설명 |
|---|---|
| 재실행 단위가 다르다 | 시드만 다시 넣고 싶은 일이 자주 생긴다(데모 리허설). V2는 `TRUNCATE ... RESTART IDENTITY CASCADE`로 시작해 **단독 재실행이 가능**하다 |
| 리뷰 단위가 다르다 | DDL 변경은 팀 전체에 영향이 있고, 시드 변경은 시연에만 영향이 있다 |
| 실패 원인 분리 | 마이그레이션이 죽었을 때 "구조 문제인가 데이터 문제인가"가 파일명으로 갈린다 |

```
V1__schema.sql    Core 8 테이블 · CHECK 17 · 인덱스 6 · 코멘트 27      (구조)
V2__seed.sql      마스터 + 감사 로그 100 + 데모 백업 3                  (데이터)
V3__embargo.sql   스키마 확장 + 홍보팀 데이터                           (구조 + 데이터)
```

V3가 둘을 겸하는 이유는 §4에 있다.

## 3. 시드의 PK를 명시 지정했다 — 03번이 넘긴 Q2

```sql
INSERT INTO department (dept_id, code, name) VALUES
    (1, 'DEV', '개발팀'), ...
```

시퀀스에 맡기지 않고 PK를 SQL에 박았다.

| 대상 | PK 명시 | 이유 |
|---|---|---|
| `department` `app_user` `policy` `policy_rule` | ✅ | **런타임 삽입 경로가 없다**(정책 편집 UI 없음, 0.3). 규칙 코드가 계약·테스트·프론트 픽스처에서 고정 ID로 참조된다 |
| `message` `inspection` `inspection_finding` (V2) | ✅ | 데모 URL `/inspections/{id}`가 걸려 있다. `RESTART IDENTITY`만 믿으면 INSERT 순서 변화에 ID가 밀린다 |
| `message` `inspection` `inspection_finding` (V3) | ❌ **시퀀스 채번** | §5의 장애 참조 |

배정: 마스터 1~N / 감사 로그 1~100 / 데모 백업 101~103.
`message_id = inspection_id`로 맞춰 두면 디버깅 때 눈으로 따라가기 쉽다.

### 시퀀스 재동기화 — 빠뜨리면 첫 API 호출이 죽는다

PK를 명시하면 시퀀스는 그대로 1이다. 파일 끝에서 맞춘다.

```sql
SELECT setval(pg_get_serial_sequence('message','message_id'), (SELECT max(message_id) FROM message));
```

**이걸 빼면 사용자의 첫 프롬프트 제출이 `duplicate key`로 실패한다.**
V2 §8과 V3 §6이 그 자리다.

## 4. V3 — 나중에 추가된 요구사항을 얹는 방법 (03번이 넘긴 Q4)

홍보팀 엠바고 정책(DR-11 · 소유 부서≠적용 부서, DR-12 · 규칙의 유효기간)은 **V1·V2가 이미 적용된 뒤에** 결정됐다.

### 4.1 V1을 고치지 않았다

| 상황 | 규칙 |
|---|---|
| 로컬에만 적용됨 | V1을 고치고 `DROP SCHEMA public CASCADE` 후 재적용. **팀원에게 통보 필수** |
| 공유 DB/CI에 적용됨 | **V1 불변.** 변경분을 새 버전 파일로 추가 |

V3 시점에는 CI와 팀원 로컬에 이미 V1·V2가 적용되어 있었다.
적용된 마이그레이션을 수정하면 Flyway가 체크섬 불일치로 기동을 거부한다 — 그게 정상 동작이다.

### 4.2 V3가 한 일

```sql
-- 스키마 확장
ALTER TABLE policy      ADD COLUMN owner_dept_id BIGINT;        -- DR-11(소유 부서≠적용 부서)
ALTER TABLE policy_rule ADD COLUMN embargo_until DATE;          -- DR-12(규칙의 유효기간)
ALTER TABLE policy DROP CONSTRAINT chk_policy_category;         -- EMBARGO 추가
ALTER TABLE policy ADD  CONSTRAINT chk_policy_category CHECK (category IN ('PII','SECRET','CONFIDENTIAL','EMBARGO'));

-- 데이터
INSERT INTO department (dept_id, code, name) VALUES (5, 'PR', '홍보팀');
UPDATE policy SET owner_dept_id = 4 WHERE code IN ('P-PII','P-SEC','P-CONF');  -- 기존 행 보정
INSERT INTO policy ... P-EMBARGO ...
INSERT INTO policy_rule ... EMB-NOVA-01, EMB-ATLAS-02 ...
INSERT INTO department_policy VALUES (1,4), (2,4);              -- DEV, SALES
```

**추가 컬럼은 nullable로 넣고 UPDATE로 채운다.** `NOT NULL`로 바로 추가하면 기존 3개 정책 행이
제약을 만족하지 못해 `ALTER`가 실패한다. 03번 §5가 `owner_dept_id`의 nullable을 유지한 이유가 이것이다.

### 4.3 V3가 구조와 데이터를 겸한 이유

§2의 분할 원칙(V1=구조 / V2=데이터)에 대한 예외다.

엠바고는 **컬럼 없이는 데이터가 들어갈 수 없고, 데이터 없이는 컬럼이 의미가 없다.**
`V3__schema`와 `V4__seed`로 나누면 둘 사이에 "컬럼은 있는데 정책이 없는" 중간 상태가 생기며,
그 상태로 배포된 서버는 홍보팀 화면이 비어 있다. 하나의 요구사항은 하나의 마이그레이션으로 끝낸다.

## 5. 실제로 겪은 장애와 그 수정

### 5.1 V3 시드가 운영 DB의 PK를 침범해 기동 실패 (2026-09-03)

**증상:** 이미 사용 중이던 DB에 V3를 적용하자 `duplicate key` 로 마이그레이션이 통째로 실패하고
백엔드가 기동하지 못했다.

**원인:** V3 초안이 홍보팀 감사 로그 5건의 `message_id`를 104~108로 하드코딩했다.
그 DB에는 이미 사용자가 보낸 프롬프트가 104번 이후를 쓰고 있었다.

**수정:** `message` · `inspection` · `inspection_finding`은 **시퀀스에서 채번**하도록 바꾸고,
행 구분은 헬퍼 테이블의 `seq`와 `marker`로 한다. 채번된 `message_id`는 본문 join으로 되받는다.

```sql
INSERT INTO message (user_id, original_text, submitted_text, status, created_at)
SELECT 5, r.original_text, r.original_text, r.status, r.created_at FROM seed_pr_row r ORDER BY r.seq;

CREATE TABLE seed_pr_msg AS
SELECT m.message_id, r.seq, r.marker, ...
  FROM seed_pr_row r JOIN message m ON m.original_text = r.original_text AND m.user_id = 5;
```

**교훈이 규칙이 됐다:**

> **런타임 삽입 경로가 있는 테이블의 PK는 마이그레이션에서 하드코딩하지 않는다.**
> V2는 빈 DB에만 적용되므로 하드코딩이 안전했지만, V3는 이미 데이터가 있는 DB에 적용된다.
> **같은 프로젝트 안에서도 마이그레이션 버전마다 전제가 다르다.**

`department`·`app_user`·`policy`·`policy_rule`은 V3에서도 PK를 명시한다 — 런타임 삽입 경로가 없기 때문이다.

### 5.2 정규식 리터럴에서 백슬래시가 유실될 뻔했다

PostgreSQL은 `standard_conforming_strings = on`이 기본이므로 일반 문자열 `'…'`에서 `\`가 보존된다.
**`E'…'`를 쓰면 `\d`가 `d`로 유실된다** — 규칙이 조용히 아무것도 매칭하지 않게 된다.

**규칙: 마이그레이션에 `E''` 리터럴을 쓰지 않는다.** V2·V3에 한 개도 없다.
검증은 07번 §4의 기획서 7.2(규칙 10종) ↔ DB 바이트 대조로 한다.

### 5.3 `random()`이 두 테이블에서 다른 값을 냈다

감사 로그 100건의 `created_at`이 `now() - (random() * interval '7 days')`인데,
`message`와 `inspection`을 각각 INSERT하면 두 문장에서 `random()`이 따로 불려 시각이 어긋난다.

**해결:** 파생값을 헬퍼 테이블(`seed_audit_row`)에 **한 번 계산해 고정**한 뒤 각 테이블이 그것을 읽는다.
헬퍼 테이블은 마이그레이션 끝에서 `DROP`한다.

## 6. 재작업 규칙 (요약)

| 하고 싶은 것 | 방법 |
|---|---|
| 시드만 다시 넣기 | V2를 그대로 실행. `TRUNCATE ... RESTART IDENTITY CASCADE`로 시작하므로 재실행 가능 |
| 로컬 DB 처음부터 | `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` 후 `./gradlew bootRun` |
| 적용된 마이그레이션 수정 | **하지 않는다.** 새 버전 파일을 추가한다 |
| 규칙 하나 변경 | 아래 6곳을 함께 고친다 |

```bash
# 시드 단독 재적용
docker exec -i gateway-pg psql -U gateway -d gateway -v ON_ERROR_STOP=1 \
  < backend/src/main/resources/db/migration/V2__seed.sql
```

### 규칙 하나를 바꾸면 함께 고쳐야 하는 6곳

| # | 위치 | 빠뜨리면 |
|---|---|---|
| 1 | `V*__*.sql` | 실서버 판정이 안 바뀐다 |
| 2 | `frontend/dev/fixture-server.js`의 `RULES` | **픽스처 모드와 실서버가 다른 판정을 낸다** |
| 3 | 기획서 7.2(규칙 10종) | SSOT가 거짓이 된다 |
| 4 | `docs/api-spec.md` | 계약과 구현이 갈린다 |
| 5 | 계약 확정본 | 다른 컴포넌트가 옛 값을 믿는다 |
| 6 | 테스트 기대값 | CI가 초록인데 동작이 틀리다 |

## 7. 검증 — 이 설계가 실제로 재현되는가

빈 스키마에서 Flyway가 V1→V2→V3를 처음부터 적용하는 것을 확인했다.

```
installed_rank | version | description | success | 소요
       1       |    1    |   schema    |    t    |  44ms
       2       |    2    |    seed     |    t    | 270ms
       3       |    3    |   embargo   |    t    |  20ms
```

이어서 `ddl-auto: validate` 통과 + 테스트 41건 전부 통과. 상세는 [07 검증 보고서](07_스키마검증보고서.md).
