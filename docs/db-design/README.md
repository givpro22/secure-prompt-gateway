# 데이터 아키텍처 산출물 (Data Architect)

이 폴더는 **DB 설계가 어떤 순서로, 무엇을 근거로 만들어졌는지**를 복원한 문서 묶음이다.

단일 진실 원천(SSOT)은 여전히 `사내_AI_게이트웨이_기획서_v1.md`이고, 실행되는 정답은
`backend/src/main/resources/db/migration/V*.sql`이다. 이 폴더는 그 둘 사이의 **판단 과정**을 남긴다.

---

## 왜 이 폴더가 필요한가

구현이 먼저 완성된 뒤에 문서를 쓰면, 설계가 결과에서 역산된 것처럼 보인다.
그러면 발표에서 "왜 이 테이블입니까"라는 질문에 "그렇게 만들어져 있습니다"밖에 답하지 못한다.

DA의 작업은 원래 다음 순서다. 이 폴더는 각 단계를 **그 단계에서 알 수 있었던 것만으로** 재구성했다.

```
① 요구사항 정의    "무엇을 저장해야 하는가"        ← 기획서 3·4·5·7장에서 도출
        ↓
② ERD 설계         "어떤 개체와 관계로 나눌 것인가"  ← 정규화·카디널리티 결정
        ↓
③ 스키마 설계      "어떤 타입·제약으로 못 박을 것인가" ← 물리 모델
        ↓
④ 마이그레이션     "어떻게 재현 가능하게 적용할 것인가" ← Flyway V1·V2·V3
        ↓
⑤ 엔티티/리포지토리 "애플리케이션이 어떻게 읽고 쓰는가"  ← JPA 매핑
        ↓
⑥ 추적/검증        "요구사항이 실제로 반영되었는가"    ← RTM + 검증 실행
```

## 표기법 — 이 묶음에서 쓰는 코드 세 가지

문서 안에 `DR-01`, `UC-03`, `D14` 같은 코드가 나온다. **출처가 서로 다르다.**
본문에서는 항상 `DR-01 · 원문/전송본 분리`처럼 이름을 붙여 쓰므로 이 표로 돌아올 일은 거의 없다.

| 코드 | 뜻 | 누가 정했나 | 원본 |
|---|---|---|---|
| **UC**-nn | Use-Case. 사용자가 **무엇을 하는가** | 기획서에 원래 있던 것 | 기획서 3.2 |
| **D**n | Decision. 기획서의 모순·미정 항목을 **어떻게 결정했는가** | 팀이 2026-09-02에 결정 | 기획서 0.5 |
| **DR**-nn | Data Requirement. **무엇을 저장해야 하는가** | **DA가 이 묶음에서 새로 붙인 번호** | [01번 문서](01_데이터요구사항정의서.md) |

`DR`은 기획서에 없다. Use-Case는 "사용자가 무엇을 하는가"이지 "무엇을 저장해야 하는가"가 아니어서,
기획서 3·4·5·7장에서 데이터 관점으로 다시 도출해 번호를 붙였다.
번호가 있어야 [06번 추적 매트릭스](06_요구사항추적매트릭스.md)에서
**요구사항 → 컬럼 → 마이그레이션 → 엔티티 → API/화면**을 한 줄로 이을 수 있다.

> **발표 주의:** `UC`와 `D`는 팀 공용어지만 **`DR`은 이 묶음 안에서만 쓰는 말이다.**
> 다른 조원이나 교수님은 `DR-07`이 뭔지 모른다. 말할 때는 번호 대신 이름을 쓴다.

> 그 판정이 어떤 정책 **버전**으로 내려졌는지는 `inspection.policy_snapshot`에 시점 보존됩니다."
