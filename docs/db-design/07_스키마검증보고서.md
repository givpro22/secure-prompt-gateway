## 3. 업무 불변식 (실데이터 108건)

| # | 불변식 | 근거 | 위반 |
|---|---|---|---|

| 2 | 사람 확정 BLOCKED는 본문 **보존** | D14(BLOCK⇒NULL은 필요조건) | **0** (해당 1건 본문 있음) |
| 3 | PENDING_REVIEW는 본문 보존 | D7(PENDING_REVIEW 본문 보존) | **0** |
| 4 | RULE finding은 `review_status='CONFIRMED'` | D6(review_status 4값) | **0** |
| 5 | AI finding은 `rule_id IS NULL` | 6.2 | **0** |

**불변식 1·2가 함께 통과한 것이 중요하다.** `BLOCKED ⇒ NULL`은 **거짓**이고

**불변식 4는 CHECK가 아니라 코드 규약이 지킨다**([03 §4.3](03_스키마설계서.md), [05 §7](05_엔티티매핑설계서.md)).

✓ PII-CARD-02    (21자)     ✓ SEC-DBURL-02   (36자)

**백슬래시가 살아 있다** — [04 §5.2](04_마이그레이션설계서.md)의 `E''` 금지 규칙이 지켜졌다는 뜻이다.
`\d`가 `d`로 유실됐다면 규칙이 조용히 아무것도 매칭하지 않는다.

## 5. 제약 부정 테스트 — DR-20(값 집합 DB 강제)이 실제로 막는가

전부 트랜잭션 안에서 실행 후 롤백했다.

| # | 시도 | 기대 | 실제 |
|---|---|---|---|
| 1 | `review_status` 미지정 INSERT | `SUGGESTED` 저장 | ✅ `SUGGESTED` — **DR-05(AI 후보는 확정 전 무효)가 DB 수준에서 강제됨** |
| 2 | `review_status='APPROVED'` | 거부 | ✅ `chk_finding_review_status` 위반 |
| 3 | `source='AI'` + `rule_id=1` | 거부 | ✅ `chk_finding_ai_no_rule` 위반 |
| 4 | `action='MASK'` + `mask_label` 없음 | 거부 | ✅ `chk_rule_mask_label` 위반 |
| 5 | `policy.category='OTHER'` | 거부 | ✅ `chk_policy_category` 위반 |
| 6 | `app_user.dept_id=999` | 거부 | ✅ `fk_app_user_dept` 위반 |
| 7 | `department_policy` 중복 매핑 | 거부 | ✅ `pk_department_policy` 위반 |

**테스트 1이 4장 책임 경계의 물증이다.** 엔티티를 우회한 직접 INSERT인데도 `SUGGESTED`가 박힌다 —
"AI는 결정하지 못한다"가 코드가 아니라 **스키마의 성질**이다.

## 7. 발견 사항

치명적 결함은 없다. 아래 5건은 개선·동기화 항목이다.

### ⚠️ F-01 (개선) — `inspection`에 `(message_id, phase)` 유일 제약이 없다

**기획서 6.3(관계 정의):** "message — inspection 1:N, **phase별 1건**"

**실측:** 같은 `message_id`에 `phase='INPUT'` inspection을 2건 삽입했더니 **성공했다.**

```sql
insert into inspection (message_id, phase, ...) values (1, 'INPUT', ...);  -- 통과
select count(*) from inspection where message_id=1 and phase='INPUT';      -- 2
```

**영향:** 현재 데이터는 위반 0건이고, `InspectionService`가 message당 1건만 만든다.
다만 재시도 로직이나 동시 요청이 들어오면 감사 목록에 같은 프롬프트가 두 줄로 뜬다.
**"phase별 1건"이 설계 의도인데 스키마가 강제하지 않는 유일한 관계 제약이다.**

**제안 (V4 후보):**
```sql
ALTER TABLE inspection ADD CONSTRAINT uq_inspection_message_phase UNIQUE (message_id, phase);
```
현재 데이터가 위반 0건이므로 무중단으로 추가 가능하다.

---

### ⚠️ F-02 (개선) — `inspection_finding.category`에만 CHECK가 없다

enum 성격의 컬럼 중 **이것 하나만** CHECK가 없다.

**실측:** `category='NOT_A_CATEGORY'` 삽입이 **성공했다.**

**영향이 단순한 누락보다 크다.** 엔티티는 이 컬럼을 `PolicyCategory` enum으로 매핑한다
([05 §2](05_엔티티매핑설계서.md)). 즉 **쓰기는 되는데 읽기가 터진다** —
잘못된 값이 한 번 들어가면 그 행을 포함하는 감사 목록 조회가 통째로 실패한다.
DB가 조용히 받아주고 애플리케이션이 나중에 죽는, DR-20(값 집합 DB 강제)이 막으려던 바로 그 형태다.

**제안 (V4 후보):**
```sql
ALTER TABLE inspection_finding
    ADD CONSTRAINT chk_finding_category CHECK (category IN ('PII','SECRET','CONFIDENTIAL','EMBARGO'));
```
현재 데이터는 전부 유효값이라 무중단으로 추가 가능하다.

### 📝 F-03 (문서 동기화) — `submitted_text` 설명이 D14(BLOCK⇒NULL은 필요조건) 이전 문구다

| 위치 | 현재 문구 | 문제 |
|---|---|---|
| `V1__schema.sql:117` | `NULL이면 미전송(BLOCK 판정)` | "BLOCK ⇒ NULL"로 읽힌다 |
| `docs/erd.dbml:84` | `NULL이면 미전송(BLOCK)` | 같음 |
| **기획서 6.2(테이블 상세) (정답)** | `NULL은 **마스킹본이 생성된 적이 없음**. 규칙 BLOCK 경로에서만 발생. PENDING_REVIEW와 사람이 확정한 BLOCK은 본문을 보존 (D7 · PENDING_REVIEW 본문 보존·D14 · BLOCK⇒NULL은 필요조건)` | |

**왜 중요한가:** §3 불변식 1·2가 정확히 이 지점이다. 주석을 그대로 믿고
`BLOCKED ⇒ submitted_text IS NULL` 로 테스트를 짜면 **사람 확정 BLOCK 1건 때문에 실패한다.**
DDL 주석은 스키마만 보는 사람에게 유일한 설명이라 오해 비용이 크다.

**제안:** 두 곳의 문구를 기획서 6.2(테이블 상세)에 맞춘다. `COMMENT ON COLUMN`(131행)은 `'마스킹 적용 후 본문. NULL이면 미전송'`으로
중립적이라 그대로 둬도 무방하다.

docs/erd.dbml:77  Note: '... 시드는 (SALES,P-CONF),(HR,P-CONF) 2행뿐'

### ℹ️ F-05 (정보) — V3 추가 컬럼의 물리 순서가 테이블 끝이다

`policy.owner_dept_id`와 `policy_rule.embargo_until`은 `ALTER TABLE ADD COLUMN`으로 들어가
**테이블의 마지막 컬럼**이다. 기획서 6.2(테이블 상세) 표는 각각 `scope` 뒤, `description` 뒤에 그린다.

**동작에 영향 없다.** 모든 쿼리가 컬럼명을 명시하고, `SELECT *` 의존 코드가 없다.
`\d policy` 출력 순서가 기획서 표와 다르다는 것만 알고 있으면 된다.
순서를 맞추려면 테이블 재생성이 필요한데, [04 §4.1](04_마이그레이션설계서.md)의
"적용된 마이그레이션은 고치지 않는다" 규칙에 비해 얻는 것이 없다. **수정하지 않는다.**

## 8. 의도적으로 두는 것 (발견 사항 아님)

혼동을 막기 위해 명시한다. 아래는 누락이 아니라 결정이다.

| 항목 | 결정 근거 |
|---|---|
| `department.code`에 CHECK 없음 | 부서는 조직이 늘리는 값이다. V3에서 홍보팀을 `INSERT` 한 줄로 추가할 수 있었던 이유 ([03 §3](03_스키마설계서.md)) |
| `source='RULE'` ⇒ `CONFIRMED` CHECK 없음 | 규칙 엔진이 DEFAULT INSERT 후 UPDATE하는 구현을 막지 않기 위함. 팩토리 메서드로 규약화 ([03 §4.3](03_스키마설계서.md)). **검증은 §3 불변식 4** |
| 역방향 `source='RULE'` ⇒ `rule_id` 필수 없음 | 같은 이유 ([03 §4.2](03_스키마설계서.md)) |
| Future 4 테이블 미생성 | DR-22(확장 지점 논리 표기) · 기획서 0.3(범위 상한) 범위 상한 |
| 인덱스가 108행에서 seq scan에 짐 | 설계 의도 표기용. [03 §6](03_스키마설계서.md)에 명시 |

## 9. 조치 요약

| 항목 | 등급 | 조치 | 결정권 |
|---|---|---|---|
| F-01 유일 제약 | 개선 | `V4__constraints.sql` 1줄 | 팀 합의 (스키마 변경) |
| F-02 category CHECK | 개선 | 같은 V4에 1줄 | 팀 합의 (스키마 변경) |
| F-03 주석 문구 | 문서 | V1 주석 + erd.dbml 수정 | DA 단독 가능 |
| F-04 매핑 행 수 | 문서 | erd.dbml 수정 (발표 이미지 영향) | DA 단독 가능 |
| F-05 컬럼 순서 | 정보 | **조치 없음** | — |

F-01·F-02는 **판정 결과를 바꾸지 않는다.** 현재 데이터가 두 제약을 이미 만족하므로
추가해도 기존 테스트 41건이 그대로 통과한다. 다만 [04 §4.1](04_마이그레이션설계서.md)에 따라
V1을 고치지 않고 **V4를 새로 추가**해야 한다.

## 10. Q&A 대비 — 이 보고서에서 꺼낼 카드

| 예상 질문 | 답 |
|---|---|
| "ERD가 실제 DB와 같습니까?" | 컬럼 65개를 전수 대조했고, `ddl-auto: validate`가 어긋나면 서버가 기동하지 않습니다 (§0, §2.2) |
| "정책을 DB에 뒀다는 게 무슨 의미입니까?" | 부서 매트릭스를 표에서 옮긴 게 아니라 쿼리로 역산했고 기획서와 일치합니다 (§4.3) |
| "AI가 마음대로 차단할 수 있나요?" | 엔티티를 우회한 직접 INSERT도 `SUGGESTED`로 저장됩니다 (§5 테스트 1) |
| "확장성이 있다는 근거는?" | V3가 새 정책 축(엠바고)을 추가하며 AI 관련 컬럼을 0개 추가했습니다 (§2.4) |
| "정규식이 SQL에서 깨지지 않나요?" | 기획서와 바이트 단위로 대조했습니다. `E''` 리터럴 0개 (§4.2) |
| "설계 대비 미비점은?" | 5건 있고 등급·조치·결정권까지 정리했습니다 (§7, §9) |

> 마지막 줄이 실제로는 가장 강한 카드다. **미비점을 먼저 말하는 쪽이 검증을 해 본 쪽이다.**
