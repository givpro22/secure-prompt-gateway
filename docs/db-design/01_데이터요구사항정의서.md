# 01. 데이터 요구사항 정의서

**작성 근거:** 기획서 2장(문제 정의) · 3장(Use-Case) · 4장(책임 경계) · 5장(화면) · 7장(정책·규칙) · 0.5절(결정 D1 · 중첩 억제~D20 · embargo_until 신설)
**이 문서의 위치:** ERD를 그리기 **전**에 확정되어야 하는 것. "무엇을 저장해야 하는가"만 다루고, 테이블 이름은 아직 정하지 않는다.

---

## 0. 도출 방법

데이터 요구사항은 상상해서 만들지 않는다. 세 갈래에서만 나온다.

| 갈래 | 질문 | 기획서 근거 |
|---|---|---|
| **Use-Case** | 이 행위가 끝났을 때 무엇이 남아야 하는가 | 3.2 UC-01~UC-07 |
| **화면** | 이 화면이 그리려면 무엇을 읽어야 하는가 | 5.3 SCR-01, 5.4 SCR-02 |
| **규칙·정책** | 판단의 기준이 어디에 있어야 하는가 | 7.1~7.6, 4장 책임 경계 |

여기에 가이드의 **AI-Ready 4대 원칙**이 비기능 요구사항으로 얹힌다.

## 1. 기능 데이터 요구사항

### 1.1 프롬프트와 판정 (UC-01 · 프롬프트 제출·규칙 판정 ~ UC-04 · 판정 폴링)

| ID | 요구사항 | 유래 | 이유 |
|---|---|---|---|
| **DR-01** | 사용자가 입력한 **원문**과 외부로 나가는 **전송본**을 분리해 보관한다 | UC-01(프롬프트 제출·규칙 판정), UC-02(마스킹 확인·재제출), 2.4 | 원문은 감사 증적이고 전송본은 마스킹 결과다. 한 컬럼에 덮어쓰면 "무엇이 가려졌는가"를 사후에 증명할 수 없다 |
| **DR-02** | 검사 1회의 결과가 **하나의 레코드**로 남는다 | UC-01(프롬프트 제출·규칙 판정) | 화면·API·감사 목록이 모두 "판정 1건"을 단위로 다룬다. 프롬프트와 분리해야 출력 검사(UC-08 · 출력 검사, Future Future)를 같은 구조로 붙일 수 있다 |
| **DR-03** | 판정의 **근거를 항목 단위**로 남긴다 (어떤 규칙이 어디에 걸렸는가) | UC-01(프롬프트 제출·규칙 판정), UC-06(AI 제안 확정), 2.4 | 상태만 남기면 "왜 차단됐는지"를 담당자가 재현할 수 없다. 감사 시스템의 존재 이유가 여기다 |
| **DR-04** | 근거 항목은 **출처(규칙 / AI)를 구분**할 수 있어야 한다 | 4장 책임 경계 | 규칙은 확정 판정이고 AI는 제안이다. 같은 목록에 섞이되 성격이 다르므로 구분 축이 필요하다 |
| **DR-05** | AI가 만든 근거 항목은 **사람의 확정 전에는 효력이 없다** | 4장, D6(review_status 4값) | "AI는 결정하지 못한다"가 이 서비스의 핵심 주장이다. 애플리케이션 코드로만 지키면 코드를 우회한 쓰기 한 번에 무너진다 |
| **DR-06** | 사람이 확정한 사실(**누가·언제**)을 남긴다 | UC-06(AI 제안 확정), 4장 | 사후 소명의 대상이 사람이다. `decidedBy=HUMAN`과 담당자 식별이 함께 있어야 한다 |
| **DR-07** | AI 판정은 **비동기**이므로 진행 상태를 추적할 수 있어야 한다 | UC-03(AI 판정 요청·비동기), UC-04(판정 폴링), 8.5 | 202 + 폴링 흐름. `대기중`·`완료`·`실패`·`호출안함`이 구분되지 않으면 화면이 무엇을 그릴지 결정하지 못한다 |
| **DR-08** | 판정 결과와 프롬프트의 **상태가 서로 모순되지 않아야** 한다 | 7.5 충돌 해결 | `BLOCKED`인데 판정이 `ALLOW`인 행이 생기면 감사 데이터 전체의 신뢰가 깨진다 |

### 1.2 정책과 규칙 (UC-07 · 부서 정책 조회, 7장)

| ID | 요구사항 | 유래 | 이유 |
|---|---|---|---|
| **DR-09** | 판단의 기준(패턴·액션·심각도)은 **코드가 아니라 데이터**로 존재한다 | 11.3, 7.2 | 규칙 하나 바꾸는 데 배포가 필요하면 "정책 게이트웨이"가 아니라 그냥 하드코딩된 필터다 |
| **DR-10** | 정책은 **부서마다 다르게** 적용된다. 전사 공통 정책과 부서 한정 정책이 공존한다 | 7.3 매트릭스, UC-07(부서 정책 조회) | 개발팀에는 P-CONF가 적용되지 않는다는 것이 데모 Case B/C의 근거다. 이 차이를 표현하지 못하면 시연이 성립하지 않는다 |
| **DR-11** | 정책을 **만든 부서**와 **적용받는 부서**는 다를 수 있다 | D19(owner_dept_id 신설), 7.1 | 엠바고는 홍보팀이 걸고 개발팀·영업팀이 걸린다. 두 개념을 한 축으로 합치면 "홍보팀이 자기 엠바고에 걸린다"는 모순이 생긴다 |
| **DR-12** | 규칙에는 **유효기간**이 있을 수 있다 | D20(embargo_until 신설), 7.2 | 엠바고는 해제일이 지나면 자동으로 풀려야 한다. 날짜를 코드나 화면에 박으면 DR-09(기준은 코드가 아니라 데이터)가 무너진다 |
| **DR-13** | 규칙의 **식별 코드**가 화면·로그·API·테스트에서 동일하게 쓰인다 | 7.2, 계약서 §4 | `PII-RRN-01`이 발표 대사이자 응답 필드이자 테스트 기대값이다. 전역 유일해야 한다 |
| **DR-14** | 마스킹 라벨은 **마스킹 액션 규칙에만** 존재한다 | D5(BLOCK이면 마스킹 안 함), 7.5 | 차단 규칙에 라벨이 없는데 마스커가 호출되면 실행 시점에 죽는다. 데이터 단계에서 막아야 한다 |

### 1.3 감사와 시점 보존 (UC-05 · 감사 목록 조회, SCR-02)

| ID | 요구사항 | 유래 | 이유 |
|---|---|---|---|
| **DR-15** | 판정이 **어떤 정책 버전으로** 내려졌는지 시점 보존한다 | 6.4, 8.4 | 정책은 나중에 바뀐다. 지금 정책으로 과거 판정을 재해석하면 감사가 성립하지 않는다 |
| **DR-16** | 감사 목록을 **부서·상태·기간**으로 필터하고 **최신순**으로 정렬한다 | 5.4 SCR-02 | 조회 패턴이 고정이므로 인덱스 설계의 근거가 된다 |
| **DR-17** | 근거 항목의 위치(**오프셋**)는 원문 기준으로 저장하고 재계산하지 않는다 | D3(span 재계산 안 함) | 마스킹으로 길이가 변하므로 전송본 기준으로는 위치가 어긋난다. 화면 하이라이트는 라벨 문자열 검색으로 처리한다 |

## 2. 비기능 데이터 요구사항

| ID | 요구사항 | 유래 | 이유 |
|---|---|---|---|
| **DR-19** | AI 응답 원본을 **스키마 변경 없이** 보관한다 | AI-Ready · Structured Data | 실제 LLM으로 교체하면 응답 필드가 늘어난다. 그때마다 컬럼을 추가하면 "AI-Ready"라는 주장이 거짓이 된다 |
| **DR-20** | 값 집합(enum 성격)은 **DB 수준에서 강제**한다 | 4장, D6(review_status 4값) | 애플리케이션에만 두면 시드 SQL·수동 패치·다른 컴포넌트의 직접 쓰기로 오염된다. 감사 데이터에서 그건 조용한 오염이다 |
| **DR-21** | 시드 데이터에 **실제 개인정보 형태 문자열을 넣지 않는다** | 10.1, 10.5 | 개인정보 보호를 주제로 한 서비스가 자기 시드에 주민번호를 넣으면 발표에서 그 자리에서 지적당한다 |
| **DR-22** | 범위 밖 확장 지점을 **논리 모델로 표기**한다 (DDL은 만들지 않는다) | 0.3, 6.5, 17장 | 확장성을 주장하려면 자리를 그려야 하고, 범위를 지키려면 실행하지 않아야 한다. 두 요구를 동시에 만족하는 방법이 Logical-only 표기다 |

## 3. 명시적으로 요구하지 **않는** 것

범위 상한(기획서 0.3(범위 상한))이 데이터 모델에도 그대로 적용된다. 아래는 만들지 않는다.

| 제외 항목 | 근거 | 확장 시 위치 |
|---|---|---|
| 계정·비밀번호·권한 테이블 | 0.3 — 로그인 미구현 | 17장 |
| 첨부파일 바이너리 저장 | 0.3 — 프론트에서 텍스트 추출 후 기존 경로로 전송 (D17 · 파일 입력은 기존 경로) | `attachment` (Future) |
| 정책 변경 이력 테이블 | 0.3 — 정책 편집 UI 없음. `policy.version` + 스냅샷으로 대체 | `policy_audit` (Future) |
| 출력(AI 응답) 검사 결과 | 0.3 — 입력 검사만 | `inspection.phase='OUTPUT'` 자리만 확보 |
| 모델 파라미터 테이블 | 11.3 — 현재는 환경변수 (Config Isolation) | `ai_provider_config` (Future) |

`inspection.phase`처럼 **컬럼은 만들되 값은 하나만 쓰는** 방식이 요구사항 DR-22(확장 지점 논리 표기)의 구현 형태다.
테이블을 미리 만들면 범위 위반이고, 자리조차 없으면 확장성 주장이 근거를 잃는다.

## 4. 다음 단계로 넘기는 것

이 문서는 **테이블 이름을 정하지 않았다.** 그것이 02번 ERD 설계서의 일이다.

넘기는 질문:
1. DR-01(원문/전송본 분리)의 원문·전송본은 한 테이블인가 두 테이블인가
2. DR-03(근거를 항목 단위로)의 근거 항목을 규칙 출처와 AI 출처로 **나눌 것인가 합칠 것인가** (DR-04 · 근거의 출처 구분와 상충하는가)
3. DR-10(부서별 적용 정책)의 부서×정책을 어떤 카디널리티로 표현할 것인가
4. DR-15(정책 버전 시점 보존)의 시점 보존을 이력 테이블로 할 것인가 스냅샷으로 할 것인가
5. DR-19(스키마 변경 없이 AI 응답 보관)의 "스키마 변경 없이"를 어떤 타입으로 달성할 것인가
