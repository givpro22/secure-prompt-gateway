## 2. 값 집합을 Java enum으로 (04번이 넘긴 Q1)

CHECK 제약의 값 목록을 그대로 Java `enum` 14개로 옮기고 `@Enumerated(EnumType.STRING)`으로 매핑한다.

```java
@Enumerated(EnumType.STRING)
@Column(name = "review_status", nullable = false, length = 20)
private ReviewStatus reviewStatus;
```

**`EnumType.ORDINAL`을 쓰지 않는다.** 서수로 저장하면 enum 상수 순서를 바꾸는 순간
기존 데이터의 의미가 통째로 뒤집힌다. 감사 데이터에서 이건 복구 불가능한 오염이다.
문자열로 저장하면 DB만 봐도 값이 읽히고, CHECK 제약과 **같은 문자열**로 대조된다.

### enum ↔ CHECK 대조 (14종 전부 일치)

| enum | 값 | 대응 CHECK |
|---|---|---|
| `UserRole` | EMPLOYEE, SECURITY_ADMIN | `chk_app_user_role` |
| `PolicyCategory` | PII, SECRET, CONFIDENTIAL, EMBARGO | `chk_policy_category` |
| `PolicyScope` | GLOBAL, DEPT | `chk_policy_scope` |
| `RuleType` | REGEX, KEYWORD | `chk_rule_type` |
| `RuleAction` | MASK, BLOCK, REVIEW | `chk_rule_action` |
| `Severity` | HIGH, MEDIUM, LOW | `chk_rule_severity` |
| `Obligation` | LEGAL, INTERNAL | `chk_rule_obligation` |
| `MessageStatus` | ALLOWED, MASKED, BLOCKED, PENDING_REVIEW | `chk_message_status` |
| `InspectionPhase` | INPUT, OUTPUT | `chk_inspection_phase` |
| `AiStatus` | SKIPPED, PENDING, COMPLETED, FAILED | `chk_inspection_ai_status` |
| `FinalDecision` | ALLOW, MASK, BLOCK, PENDING | `chk_inspection_final_decision` |
| `DecidedBy` | RULE, HUMAN | `chk_inspection_decided_by` |
| `FindingSource` | RULE, AI | `chk_finding_source` |
| `ReviewStatus` | SUGGESTED, ACCEPTED, REJECTED, CONFIRMED | `chk_finding_review_status` |

> **이중 방어의 구조:** Java enum이 애플리케이션 경로를 막고, CHECK가 그 외 모든 경로를 막는다.
> 어느 한쪽만 있으면 뚫린다. 07번 §5가 실제로 뚫리지 않는 것을 확인한다.

## 3. JSONB를 타입 있는 객체로 (04번이 넘긴 Q2)

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "policy_snapshot", nullable = false, columnDefinition = "jsonb")
private PolicySnapshot policySnapshot;
```

Hibernate 6의 `@JdbcTypeCode(SqlTypes.JSON)`으로 `record`와 직접 왕복한다.

```java
public record RuleResult(List<RuleMatch> matches, List<String> appliedRuleCodes) { ... }
public record PolicySnapshot(List<PolicyRef> policies) { ... }
```

| 대안 | 기각 사유 |
|---|---|
| `String` 필드 + 수동 `ObjectMapper` | 서비스 계층마다 파싱·직렬화 코드가 흩어진다. 오타가 런타임에야 드러난다 |
| `Map<String,Object>` | 필드명이 문자열 키라 컴파일러가 아무것도 잡아주지 못한다 |

**이것이 발표에서 AI-Ready "Structured Data" 원칙의 물증이다.**
AI 응답 스키마가 늘어나면 `record`에 필드를 추가할 뿐 **마이그레이션이 없다**.

```
policy_snapshot → PolicySnapshot[policies=[PolicyRef[policyId=1, code=P-PII, version=3, ruleCodes=[...]]]]
rule_result     → RuleResult[matches=[RuleMatch[..., span=[18,26], matchedKeyword=null, ...]], appliedRuleCodes=[...]]
ai_result       → AiAssessment[riskCandidates=[RiskCandidate[..., evidence=[Evidence[...]]]], reviewRequired=true]
```

> `RuleMatch.embargoUntil`은 `LocalDate`가 아니라 `String`이다.
> 이 record는 API 응답 JSON에 그대로 실리므로, 날짜 형식이 Jackson 설정에 좌우되면 계약이 흔들린다.

## 4. 복합 PK 매핑 (04번이 넘긴 Q3)

`department_policy`는 `(dept_id, policy_id)` 복합 PK다.

```java
@Embeddable
public class DepartmentPolicyId implements Serializable {
    @Column(name = "dept_id")   private Long deptId;
    @Column(name = "policy_id") private Long policyId;
}

@Entity @Table(name = "department_policy")
public class DepartmentPolicy {
    @EmbeddedId private DepartmentPolicyId id;
    ...
}
```

| 대안 | 기각 사유 |
|---|---|
| `@IdClass` | 필드를 엔티티와 ID 클래스 양쪽에 중복 선언해야 한다 |
| `@ManyToMany` 로 매핑 테이블 감추기 | `applied_at` 컬럼을 가질 수 없고, 매핑 존재 여부를 직접 조회하지 못한다. 정책 로드 쿼리가 `exists (...)`로 이 테이블을 직접 본다 |

## 5. `ddl-auto: validate` — 사람이 대조표를 만들지 않는다

```yaml
spring.jpa.hibernate.ddl-auto: validate
```

기동 시 Hibernate가 **엔티티 65개 필드와 DDL 65개 컬럼**을 이름·타입 단위로 대조한다.
어긋나면 애플리케이션이 뜨지 않는다.

> **발표에서 쓸 문장:** "엔티티와 DDL이 일치한다는 것을 문서로 주장하지 않습니다.
> 일치하지 않으면 서버가 기동하지 않습니다."

`update`나 `create`를 쓰지 않는 이유는 04번 §1에 있다 — 그쪽은 엔티티에서 DDL을 역산하므로
CHECK 제약·코멘트·인덱스가 전부 사라진다.

## 6. Repository 설계

### 6.1 정책 로드 — 규칙 엔진의 입구

`PolicyRuleRepository.findActiveByDept(deptId)` 하나가 **기획서 7.3(부서 매트릭스) 매트릭스 전체를 대신한다.**

```java
where r.isActive = true and p.isActive = true
  and (p.scope = GLOBAL
       or exists (select 1 from DepartmentPolicy dp
                   where dp.id.policyId = p.policyId and dp.id.deptId = :deptId))
order by <REGEX 먼저>, <severity 내림차순>, r.code
```

**정렬이 곧 실행 순서다.** 기획서 7.4(판정 절차)-4·7.4-5가 "REGEX를 severity 내림차순으로 먼저,
그 다음 KEYWORD"라고 정했고, 동률은 rule code 사전순(7.6의 라벨 충돌 해결과 같은 기준)이다.
쿼리에서 순서를 보장하면 엔진이 정렬을 다시 하지 않는다.

이 시그니처는 **DA → 규칙 엔진 인계 계약**이므로 바꾸지 않는다.

### 6.2 감사 목록의 선택 필터 (04번이 넘긴 Q4) — 겪은 문제와 해결

**처음 시도(실패):** JPQL의 `(:param is null or ...)` 관용구

```
and (:from is null or i.createdAt >= :from)
```
```
ERROR: could not determine data type of parameter $5
```

`OffsetDateTime` null을 바인딩하면 JDBC 드라이버가 타입 OID를 보내지 못하고,
PostgreSQL이 `$5 IS NULL`의 타입을 결정하지 못한다.
`deptId`(bigint)·`status`(varchar)는 통과하는데 **타임스탬프만** 죽어서 더 헷갈렸다.

**해결:** `JpaSpecificationExecutor` + `InspectionSpecs`

```java
public static Specification<Inspection> of(Long deptId, MessageStatus status,
                                           OffsetDateTime from, OffsetDateTime to) {
    // null인 필터는 Specification 자체를 만들지 않는다 → SQL에 나가지 않는다
}
```

"값이 없으면 전체"가 조건 부재로 자연스럽게 성립한다. null 파라미터가 애초에 SQL에 도달하지 않는다.

> 경계 처리: `to`는 **미만**(`<`)이다. 포함하면 하루 단위 필터가 다음 날 00:00을 삼킨다.

### 6.3 N+1 방지

목록 조회에 `@EntityGraph`를 붙였다.

```java
@EntityGraph(attributePaths = {"message", "message.user", "message.user.department"})
```

없으면 20행 목록에서 부서·사용자 조회가 **행마다** 나간다(1 + 20×3 쿼리).
감사 목록은 `deptId` 필터와 부서명 표시 때문에 항상 이 경로를 탄다.

## 7. 팩토리 메서드로 지키는 규약

03번 §4.3에서 **CHECK로 걸지 않기로 한 규칙**이 하나 있다 —
"규칙 finding의 `review_status`는 CONFIRMED 고정"(D6 · review_status 4값).

제약 대신 엔티티 팩토리가 강제한다.

```java
InspectionFinding.ofRule(inspection, rule, category, spanStart, spanEnd)  // → CONFIRMED 고정
InspectionFinding.ofAi(inspection, code, category, rationale, evidence)   // → SUGGESTED (DB DEFAULT)
```

setter로 임의 조립하는 경로를 열어두지 않았다. **제약이 아닌 규약이므로 검증이 필요하고,
그 검증을 [07 검증 보고서 §3](07_스키마검증보고서.md)이 데이터로 수행한다.**

## 8. 매핑 요약

| 엔티티 | 테이블 | 특이사항 |
|---|---|---|
| `Department` | `department` | — |
| `AppUser` | `app_user` | `@ManyToOne` → Department |
| `Policy` | `policy` | `ownerDept` `@ManyToOne` (nullable) |
| `PolicyRule` | `policy_rule` | `embargoUntil` `LocalDate` |
| `DepartmentPolicy` | `department_policy` | `@EmbeddedId` |
| `Message` | `message` | `submittedText` nullable — 의미를 갖는 NULL |
| `Inspection` | `inspection` | JSONB 3 |
| `InspectionFinding` | `inspection_finding` | JSONB 1, nullable FK 2, 팩토리 2 |

모든 `@ManyToOne`은 `FetchType.LAZY`다. 기본값 EAGER는 목록 조회에서 필요 없는 조인을 끌고 온다.
