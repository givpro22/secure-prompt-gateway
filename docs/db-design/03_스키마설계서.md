# 03. 스키마 설계서 (물리 모델)

**입력:** [02 ERD 설계서](02_ERD설계서.md)
**출력:** `backend/src/main/resources/db/migration/V1__schema.sql` · `V3__embargo.sql`
**대상 DBMS:** PostgreSQL 16

이 문서와 DDL이 어긋나면 **DDL이 정답이다.**

---

## 1. 명명 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블 | `snake_case` 단수형 | `policy_rule`, `inspection_finding` |
| PK | `<테이블>_id` | `policy_id`, `finding_id` |
| FK 컬럼 | 참조 테이블의 PK명 유지 | `policy_rule.policy_id` |
| 제약 | `pk_` `uq_` `fk_` `chk_` + 대상 | `chk_finding_review_status` |
| 인덱스 | `idx_<테이블>_<컬럼들>` | `idx_message_user_status` |
| enum 값 | `UPPER_SNAKE` | `PENDING_REVIEW` |

**제약에 전부 이름을 붙인 이유:** 위반 시 오류 메시지에 제약명이 그대로 나온다.
`chk_finding_review_status` 라고 뜨면 원인을 즉시 안다. 익명 제약이면 시스템 생성 이름을 역추적해야 한다.

## 2. 타입 선택 기준

| 요구 | 타입 | 근거 |
|---|---|---|
| PK | `BIGSERIAL` | 감사 로그는 증가만 한다. INT 상한을 걱정하지 않는 편이 싸다 |
| 코드·enum 값 | `VARCHAR(n)` + CHECK | §3 참조 |
| 본문 | `TEXT` | 프롬프트 길이 상한은 애플리케이션이 관리한다(`gateway.limits.max-input-chars`). DB가 자르면 감사 증적이 잘린다 |
| 구조화 응답 | `JSONB` | DR-19(스키마 변경 없이 AI 응답 보관). JSON이 아니라 JSONB — 파싱 결과를 저장하므로 조회·인덱싱이 가능하다 |
| 시각 | `TIMESTAMPTZ` | 타임존 없는 `TIMESTAMP`는 배포 환경(EC2 UTC)과 로컬(KST)에서 다른 값이 된다 |
| 엠바고 해제일 | `DATE` | 시각이 아니라 날짜다. `TIMESTAMPTZ`로 두면 "9월 20일 몇 시부터 풀리는가"라는 없는 질문이 생긴다 |

## 3. 값 집합을 CHECK로 강제한다 (DR-20 · 값 집합 DB 강제)

**PostgreSQL `ENUM` 타입 대신 `VARCHAR` + `CHECK`를 골랐다.**

| 기준 | ENUM 타입 | VARCHAR + CHECK ✅ |
|---|---|---|
| 값 추가 | `ALTER TYPE ... ADD VALUE` — 트랜잭션 안에서 쓸 수 없는 버전 제약이 있다 | `DROP CONSTRAINT` + `ADD CONSTRAINT` — 일반 DDL |
| JPA 매핑 | 커스텀 타입 핸들러 필요 | `@Enumerated(STRING)` 기본 지원 |
| 조회 | 캐스팅 필요한 경우 발생 | 문자열 그대로 |

**이 선택이 V3에서 값을 했다.** 엠바고 정책을 넣으며 `PolicyCategory`에 `EMBARGO`를 추가해야 했는데,
`DROP CONSTRAINT chk_policy_category` → `ADD CONSTRAINT ... IN ('PII','SECRET','CONFIDENTIAL','EMBARGO')`
두 문장으로 끝났다. ENUM 타입이었으면 마이그레이션 트랜잭션 처리를 따로 고민해야 했다.

### CHECK 제약 목록 (14개)

| 테이블 | 제약 | 허용 값 |
|---|---|---|
| `app_user` | `chk_app_user_role` | EMPLOYEE, SECURITY_ADMIN |
| `policy` | `chk_policy_category` | PII, SECRET, CONFIDENTIAL, **EMBARGO**(V3) |
| `policy` | `chk_policy_scope` | GLOBAL, DEPT |
| `policy_rule` | `chk_rule_type` | REGEX, KEYWORD |
| `policy_rule` | `chk_rule_action` | MASK, BLOCK, REVIEW |
| `policy_rule` | `chk_rule_severity` | HIGH, MEDIUM, LOW |
| `policy_rule` | `chk_rule_obligation` | LEGAL, INTERNAL |
| `policy_rule` | `chk_rule_mask_label` | §4 참조 |
| `message` | `chk_message_status` | ALLOWED, MASKED, BLOCKED, PENDING_REVIEW |
| `inspection` | `chk_inspection_phase` | INPUT, OUTPUT |
| `inspection` | `chk_inspection_ai_status` | SKIPPED, PENDING, COMPLETED, FAILED |
| `inspection` | `chk_inspection_final_decision` | ALLOW, MASK, BLOCK, PENDING |

**기획서 6.2(테이블 상세)가 명시한 CHECK는 `review_status` 하나뿐이다.** 나머지는 DA 판단으로 넓혔다 — 근거가 DR-20(값 집합 DB 강제)이다.

> `department.code`에는 CHECK를 걸지 않았다. **의도적이다.** 부서는 조직 변경으로 늘어나는 값이며,
> V3에서 홍보팀을 `INSERT` 한 줄로 추가할 수 있었던 것이 그 결과다. 정책·규칙의 값 집합은
> 설계가 결정하지만 부서 목록은 조직이 결정한다.

## 4. 업무 규칙을 제약으로 옮긴 것 (02번 Q2의 답)

ERD 단계에서 남긴 위험 — "R8·R9의 nullable을 악용한 잘못된 행" — 을 두 제약으로 막는다.

### 4.1 `chk_rule_mask_label` — DR-14(마스킹 라벨은 MASK에만)

```sql
CHECK (action <> 'MASK' OR mask_label IS NOT NULL)
```

**근거:** 기획서 7.5(충돌 해결) — "BLOCK 액션 규칙에는 mask_label이 정의되어 있지 않아 실행하면 오류가 난다."
런타임 NPE가 될 조건을 DB에서 미리 막는다.

**한 방향만 강제한다.** BLOCK/REVIEW 규칙에 라벨을 다는 것은 막지 않는다 —
의미상 무해하고, 반대 방향까지 걸면 나중에 "차단 시에도 라벨을 보여주자"는 요구를 못 받는다.

### 4.2 `chk_finding_ai_no_rule` — DR-04(근거의 출처 구분)

```sql
CHECK (source <> 'AI' OR rule_id IS NULL)
```

**근거:** 기획서 6.2(테이블 상세) — "AI 후보는 NULL."
이것이 02번 Q2에서 "합친다"고 결정한 대가를 치르는 자리다. 한 테이블에 두 출처를 담되,
AI 후보가 규칙 권위를 빌리지 못하게 한다.

**역방향(`RULE`이면 `rule_id` 필수)은 걸지 않았다.** 규칙 엔진이 rule_id 없이 finding을
만드는 경로를 막고 싶지 않았다. 3일 스프린트에서 병렬 작업 중인 컴포넌트를 막을 위험이
얻는 것보다 크다.

### 4.3 `review_status DEFAULT 'SUGGESTED'` — DR-05(AI 후보는 확정 전 무효)

```sql
review_status VARCHAR(20) NOT NULL DEFAULT 'SUGGESTED'
```

**이 한 줄이 4장 책임 경계의 세 번째 강제 지점이다** (나머지 둘은 시스템 프롬프트의 금지 조항과
JSON 스키마의 `decision` 필드 부재).

애플리케이션 기본값으로만 두면 엔티티를 우회한 `INSERT` 한 번에 AI 후보가 확정 상태로 들어간다.
DB 기본값이면 **어떤 경로로 들어와도** SUGGESTED다.

**`source='RULE'`이면 `review_status='CONFIRMED'`는 CHECK로 걸지 않았다.**
의미상 참이지만, 규칙 엔진이 DEFAULT에 기대어 INSERT한 뒤 UPDATE하는 구현을 쓰면 INSERT가 즉시 죽는다.
대신 엔티티의 `InspectionFinding.ofRule(...)` 팩토리가 CONFIRMED를 박아서 만든다.
**제약이 아니라 코드 규약으로 지키기로 한 유일한 항목이며, 검증은 07번 §3에서 데이터로 한다.**

## 5. NOT NULL을 기획서보다 조인 것

기획서 6.2(테이블 상세) 표에 제약이 안 적힌 컬럼 중 아래를 NOT NULL로 했다.

`app_user.dept_id` · `policy.is_active` · `policy_rule.is_active` ·
모든 FK(`policy_rule.policy_id`, `message.user_id`, `inspection.message_id`, `inspection_finding.inspection_id`) ·
모든 `created_at`/`applied_at`

**근거:** nullable로 두면 `is_active IS NOT FALSE` 같은 3값 논리가 정책 로드 쿼리에 번진다.
그 쿼리가 규칙 엔진의 입구다 — 거기서 한 행이 잘못 빠지면 판정이 통째로 달라진다.

**반대로 nullable을 유지한 것:**

| 컬럼 | 이유 |
|---|---|
| `message.submitted_text` | NULL이 "마스킹본 없음"이라는 **의미를 갖는다** (02번 Q1) |
| `inspection.ai_result` | BLOCK이면 AI를 호출하지 않는다 (7.5) |
| `inspection.final_decision` · `decided_by` | 판정 진행 중 상태가 존재한다 |
| `inspection_finding.rule_id` · `reviewed_by` | R8·R9. §4가 이 nullable을 조건부로 막는다 |
| `policy.owner_dept_id` | V3에서 추가된 컬럼. 기존 행을 깨지 않으려면 nullable로 넣고 UPDATE해야 한다 (04번 §4) |
| `policy_rule.embargo_until` | NULL = 기한 없는 규칙. 10종 중 8종이 그렇다 |

## 6. 인덱스 — DR-16(감사 목록 필터·정렬)의 조회 패턴에서 역산

| 인덱스 | 조회 패턴 | 유래 |
|---|---|---|
| `idx_inspection_created_at (created_at DESC)` | 감사 목록의 고정 정렬 | 5.4 SCR-02 |
| `idx_inspection_message (message_id)` | 목록·상세가 항상 message로 조인 | 8.4 |
| `idx_message_user_status (user_id, status)` | 부서 필터가 user를 거치고 status 필터가 뒤따른다 | 5.4 필터 |
| `idx_finding_inspection (inspection_id)` | 상세의 `findings[]`, 목록의 `ruleCount` | 8.4 |
| `idx_policy_rule_policy (policy_id)` | 정책 로드 조인 | 7.4-3 |
| `idx_app_user_dept (dept_id)` | 부서 필터 조인 | 5.4 |

**복합 인덱스의 컬럼 순서:** `(user_id, status)`는 부서 필터가 먼저 좁히고 상태가 뒤따르는
실제 쿼리 순서를 따른다. 뒤집으면 상태만으로 필터하는 쿼리에만 유리한데, 그런 화면은 없다.

`code` 계열에는 인덱스를 따로 만들지 않았다 — **PostgreSQL이 UNIQUE와 PK에 자동으로 인덱스를 만든다.**

> **정직하게 적어 둔다:** 시드 108행 규모에서는 여섯 개 전부 seq scan이 더 빠르다.
> 설계 의도를 남기려고 만들었다. 발표에서는 "인덱스 있습니다"가 아니라
> **"이 조회 패턴에 이 인덱스입니다"**로 말한다.

## 7. 컬럼 코멘트를 남긴 이유

`COMMENT ON COLUMN`을 27곳에 달았다. 예:

```sql
COMMENT ON COLUMN inspection_finding.review_status IS
    'SUGGESTED | ACCEPTED | REJECTED | CONFIRMED. 규칙 finding은 CONFIRMED 고정 (D6 · review_status 4값)';
```

DBeaver·DataGrip·`\d+`에서 그대로 보인다. **기획서를 열지 않고도 스키마만으로 의도가 읽히는 것**이
목표다 — 3일 뒤 다른 사람이 이 DB를 볼 때 문서가 옆에 있으리라는 보장이 없다.
