## 2. 기획서 3.3에 상세가 있는 UC — 보강 사항만

기본 흐름은 옮겨 적지 않습니다. 아래는 D1~D6 결정 이후 **3.3 표기에 압축되어 있어 오해되기 쉬운 지점**입니다.

### UC-01 보강

| # | 보강 내용 | 근거 |
|---|---|---|
| 1 | 3.3 기본 흐름 3~6단계의 실제 절차는 7.4의 8단계입니다. 특히 **6단계 중첩 억제**와 **8단계 마스킹 조건**이 3.3에는 나타나지 않습니다 | 7.4, D1, D5 |
| 2 | 중첩 억제 — 앞선 매칭의 span에 완전히 포함되는 매칭은 finding을 만들지 않습니다. Case A에서 억제되는 것은 **SEC-PRIVIP-03만이 아닙니다.** 실제로 `PII-EMAIL-04`도 `p%40ss@10.0.3.21` 구간에서 매칭되어 함께 억제됩니다(본 문서 5절 검증 결과). 최종 finding은 2건 | D1, 7.4-6 |
| 3 | 마스킹은 최종 판정이 BLOCK이 아닐 때만 실행합니다. BLOCK이면 `submitted_text`가 NULL이고 BLOCK 규칙에는 `mask_label`이 없습니다 | D5, 7.5, 7.6 |
| 4 | `appliedRuleCodes`(적용된 규칙)와 `matches`(매칭된 규칙)는 다릅니다. 억제된 규칙도 `appliedRuleCodes`에는 남습니다 | 8.4 |
| 5 | 대안 흐름 A4(REVIEW)로 분기해도 MASK가 함께 매칭되었으면 마스킹을 먼저 적용합니다 | 7.5 |

### UC-03 보강

| # | 보강 내용 | 근거 |
|---|---|---|
| 1 | AI 입력은 `maskedText`입니다. 원문(`original_text`)은 어떤 경우에도 전달하지 않습니다 | 9.3 제약 |
| 2 | BLOCK 판정이면 AiInspector를 호출하지 않습니다. 호출 자체가 없으므로 `ai_status`는 PENDING이 아니라 SKIPPED입니다 | 7.5, 8.4 |
| 3 | `hits`가 비어 있는데 호출되면 Mock이 `IllegalStateException`을 던집니다. 이것은 버그가 아니라 규칙 엔진 오류 감지 장치입니다 | 9.5 |
| 4 | 실패 경로(`ai_status = FAILED`)에서도 `message.status`는 PENDING_REVIEW로 유지되고, 판단은 SCR-02에서 사람이 합니다 | 3.3 UC-03 예외 |

### UC-06 보강

| # | 보강 내용 | 근거 |
|---|---|---|
| 1 | 검토 대상은 `source = AI` **이면서** `review_status = SUGGESTED`인 finding뿐입니다 | 3.3 UC-06 사전 조건 |
| 2 | 규칙 finding은 `review_status = CONFIRMED` 고정이며 사람의 검토 대상이 아닙니다. 화면에 ACCEPT/REJECT 버튼을 노출하지 않습니다 | D6, 6.2, 5.4 |
| 3 | 최종 판정은 ACCEPTED가 1건 이상이면 BLOCKED, 전부 REJECTED면 ALLOWED이며 두 경우 모두 `decided_by = HUMAN`입니다 (D10) | 3.3 UC-06, 6.2 |
| 4 | 이미 처리된 finding에 재요청하면 409입니다. CONFIRMED인 규칙 finding에 PATCH가 와도 409이며 에러 코드로 구분합니다 (D13) | 8.2, 8.4 |
| 5 | **ACCEPT로 BLOCKED가 되어도 `submitted_text`를 지우지 않습니다.** 담당자가 방금 판단한 근거가 사라지면 안 되기 때문이며, `submitted_text IS NULL`은 규칙 BLOCK 경로에서만 발생합니다 (D14) | 6.2, 7.5 |

## 3. 신규 상세 — UC-02 · UC-04 · UC-05 · UC-07

### UC-02 마스킹된 프롬프트 확인 및 재제출

| 항목 | 내용 |
|---|---|
| Actor | 직원 (Primary) |
| 트리거 | UC-01의 응답이 MASK(200) 또는 BLOCK(403)으로 돌아옴 |
| 사전 조건 | SCR-01 대화 영역에 판정 카드(VerdictCard)와 발화 버블(MessageBubble)이 렌더되어 있음 |
| 기본 흐름 | 1. 직원이 판정 카드에서 적용 규칙 목록(규칙 코드·카테고리·액션·의무·출처)을 확인한다 2. MessageBubble이 직원이 방금 입력한 로컬 텍스트를 표시한다 — 작성자 본인에게 자기 입력을 돌려주는 것이라 원문 미표시 원칙(감사 콘솔에서 타인의 원문)에 걸리지 않는다 (D15) 3. FE가 `submittedText`에서 `mask_label` 문자열(`[주민번호]`, `[전화번호]` 등)을 검색해 `<mark>`로 감싼다. 오프셋 산술을 하지 않는다 (D3) 4. 직원이 무엇이 치환되었는지 확인하고 대화를 계속한다 |
| 대안 흐름 A1 — 차단 후 재제출 | BLOCK(403)이면 입력창에 원문이 복원된다(5.3 인터랙션). 직원이 위반 구간을 수정해 다시 전송하면 **UC-01의 새 인스턴스**가 된다. 이전 message는 수정되지 않는다 — 8.3의 7개 엔드포인트에 message 수정 API가 없다 |
| 대안 흐름 A2 — 마스킹 후 추가 수정 | MASK(200)는 이미 마스킹본으로 전송된 상태(`status = MASKED`)이고 입력창은 비워진다(5.3). 이후 입력은 재제출이 아니라 새 프롬프트이며 동일하게 UC-01을 탄다 |
| 대안 흐름 A3 — 재제출 결과가 다시 차단 | 규칙은 결정론적이므로 같은 위반이 남아 있으면 같은 판정이 나온다. 감사 로그에는 차단 시도가 건수만큼 누적된다 |
| 사후 조건 | 재제출 시 `message` 1건과 `inspection` 1건이 **추가로** 생성된다. 차단 시도 기록은 삭제되지 않고 SCR-02 목록에 남는다 |
| 예외 E1 | 원문 복원은 클라이언트 메모리 기준이다. 새로고침하면 원문이 사라진다 — 서버는 `original_text`를 화면에 반환하지 않는다(5.4 상세 패널 1번, 원문 열람은 Future) |
| 예외 E2 | 빈 문자열·본문 누락 재전송 → 400 (8.2) |
| 검증 기준 | Case A(BLOCK) 후 입력창에 원문이 그대로 남는다 · Case D(MASK) 후 `[전화번호]`가 하이라이트된다 · 재제출 후 SCR-02 목록 건수가 1 증가한다 |
| 범위 밖 | 마스킹 구간의 부분 보존(뒤 4자리), 직원이 마스킹을 되돌리는 기능 — 7.6, 0.3 |

### UC-04 판정 상태 폴링 및 결과 확인

| 항목 | 내용 |
|---|---|
| Actor | 직원 (Primary) |
| 트리거 | UC-01의 응답이 202 Accepted, `Location` 헤더에 폴링 URL, `aiStatus = PENDING` |
| 사전 조건 | `inspection.ai_status = PENDING`. AiInspector가 @Async로 이미 호출되어 있음 (UC-03) |
| 기본 흐름 | 1. FE가 화면을 S5(스피너 + "보안 검토 중" + 경과 시간)로 전환한다 2. `Location`(또는 응답의 `inspectionId`)으로 GET `/inspections/{id}`를 호출한다 3. `gateway.polling.interval-ms`(2,000ms) 간격으로 반복한다. 응답의 `pollAfterMs`도 같은 값이다 4. `aiStatus`가 PENDING이 아니면 폴링을 중단한다 5. COMPLETED면 `aiAssessment.riskCandidates`와 `findings`(source=AI)를 **읽기 전용**으로 표시하고 화면 문구를 "검토 대기 (담당자 확정 필요)"로 바꾼다 |
| 대안 흐름 A1 — AI 실패 | `aiStatus = FAILED` → 폴링 중단, "자동 검토 실패, 담당자 확인 중" 표시. `message.status`는 PENDING_REVIEW를 유지하고 SCR-02에서 사람이 판단한다 (3.3 UC-03 예외) |
| 대안 흐름 A2 — 최대 시도 초과 | `gateway.polling.max-attempts`(30회, 약 60초) 초과 시 폴링을 중단하고 "잠시 후 다시 확인" 안내를 띄운다. 서버 상태는 바뀌지 않으며 새로고침으로 재확인한다 |
| 대안 흐름 A3 — 담당자 확정 반영 | 담당자가 UC-06으로 확정하면 최종 판정이 BLOCKED 또는 ALLOWED가 된다. 폴링은 `ai_status` 기준으로만 종료하므로 이 시점에는 이미 멈춰 있고, 결과는 **화면 재조회(새로고침)로 반영**한다. 사람의 확정 시점은 예측할 수 없어 폴링으로 따라가면 무한 폴링이 된다 (D12) |
| 사후 조건 | 화면 상태 S5. 폴링은 읽기 전용이며 `inspection` 레코드를 변경하지 않는다 |
| 예외 E1 | 404 — 존재하지 않는 inspection → 폴링 중단, 오류 표시 (8.2) |
| 예외 E2 | 네트워크 오류 → 해당 회차를 실패로 세고 다음 주기에 재시도. 연속 실패도 max-attempts에 포함한다 |
| 검증 기준 | Mock 지연 2.5초(`ai.mock.delay-ms`) 동안 스피너가 실제로 보인다 — 이 지연은 비동기 설계를 화면에 드러내기 위한 의도적 값이다(9.5, 14장) |
| 범위 밖 | WebSocket·SSE 푸시. 큐 도입(11.2에서 미도입 명시) |

### UC-07 부서별 적용 정책 조회

| 항목 | 내용 |
|---|---|

| 사전 조건 | 계정 전환 드롭다운으로 `currentUser`가 결정되어 있음 (5.2) |

## 5. UC ↔ 데모 케이스 ↔ 검증 매핑

데모 입력 문자열의 원본은 기획서 10.4입니다. 아래는 **그 문자열로 정규식을 실제 실행해 확인한 결과**이며, 규칙 엔진 단위 테스트의 기대값으로 씁니다.

| 케이스 | 계정 | 관련 UC | 매칭 원본 | 억제(D1) | 최종 finding | 판정 | HTTP | 화면 |
|---|---|---|---|---|---|---|---|---|
| A | 이OO (개발팀) | UC-01 → UC-02 | SEC-DBURL-02 `[18,56]`, PII-EMAIL-04 `[37,51]`, SEC-PRIVIP-03 `[42,51]`, PII-RRN-01 `[73,87]` | PII-EMAIL-04, SEC-PRIVIP-03 (둘 다 SEC-DBURL-02 구간에 완전 포함) | **2건** — SEC-DBURL-02, PII-RRN-01 | BLOCK | 403 | S4 |
| B | 김OO (영업팀) | UC-01 → UC-03 → UC-04 → UC-06 | CONF-CLIENT-01 (키워드 `A사` `차세대`) | — | 규칙 1건 + AI 후보 1건 | PENDING → BLOCK(HUMAN) | 202 → 200 | S5 → SCR-02 |
| C | 이OO (개발팀) | UC-01, UC-07 | 없음 (P-CONF 미적용) | — | 0건 | ALLOW | 200 | S2 |
| D (보조) | 정OO (인사팀) | UC-01 → UC-02 | PII-PHONE-03 `[8,21]` | — | 1건 | MASK | 200 | S3 |

Case A는 **원시 매칭 4건 → 억제 2건 → finding 2건**입니다. 억제 대상은 SEC-PRIVIP-03과 PII-EMAIL-04 둘이며, 단위 테스트 기대값을 이 과정으로 고정합니다 (D11). **화면과 발표 대사의 "규칙 2건"은 그대로 유효합니다.**

Case B의 키워드는 `A사`와 `차세대` 두 개가 매칭되지만 규칙은 CONF-CLIENT-01 하나입니다. **finding은 규칙당 1건, `hits[]`는 키워드당 1건**입니다 — 감사 목록의 "규칙 수"가 규칙 단위여야 5.4 도해와 맞고, 9.3의 조립 예시가 키워드 2건을 참조 근거로 넘깁니다 (D9).
