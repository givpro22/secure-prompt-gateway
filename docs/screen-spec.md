### 1.2 상태 배지 — 용어와 색상

화면 노출 용어는 기획서 5.6 고정입니다. **내부 enum 값을 화면에 그대로 쓰지 않습니다.**

| 내부 값 | 화면 표기 | 토큰 | 쓰이는 곳 |
|---|---|---|---|
| ALLOW / ALLOWED | 허용 | `green` | SCR-01 판정 카드, SCR-02 판정 컬럼 |
| MASK / MASKED | 마스킹 | `amber` | 〃 |
| BLOCK / BLOCKED | 차단 | `red` | 〃 |
| REVIEW / PENDING_REVIEW | 검토 대기 | `purple` | 〃 |
| SUGGESTED | 제안됨 | `purple` | SCR-02 AI 후보 |
| ACCEPTED | 확정(위반) | `red` | SCR-02 AI 후보 |
| REJECTED | 기각 | `gray` | SCR-02 AI 후보 |
| CONFIRMED | 확정(규칙) | `blue` | 규칙 판정 finding에 붙음. `blue`는 5.2에서 "규칙 판정 라벨"에 배정된 토큰이라 AI 후보(`purple`)와 시각적으로 갈림. **ACCEPT/REJECT 버튼은 노출하지 않음** (5.6, D6) |

배지 시각 규격 (기획서 미정 → 본 문서 제안): 높이 22px, 좌우 패딩 8px, 반경 4px, 테두리 1px 토큰색, 텍스트 12px 토큰색, 배경 `card`. 색상만으로 구분하지 않도록 항상 한글 라벨을 함께 둡니다.

### 1.3 `aiStatus` 표기 — 분석(AI)과 검토(사람)를 가른다

`aiStatus`는 상태 배지가 아니라 보조 텍스트(`gray`)로 표기합니다 (5.4 목록 컬럼). 값 라벨은 아래로 고정합니다.

| 내부 값 | 화면 표기 | 비고 |
|---|---|---|
| SKIPPED | **(공란)** | 기획서 5.4가 공란으로 지시. 범례·툴팁이 필요하면 "AI 미호출" |
| PENDING | 분석 중 | |
| COMPLETED | 분석 완료 | |
| FAILED | 분석 실패 | 상세 패널 문장도 "자동 분석 실패 — 담당자 판단이 필요합니다" |

**"검토"는 사람의 행위로 예약된 단어입니다.** 5.6이 `PENDING_REVIEW`를 "검토 대기", `REVIEW`를 "검토"로 이미 고정했고, UC-06이 사람의 확정 절차입니다. 감사 목록 한 행에 판정 "검토 대기"와 AI 상태가 나란히 서는데 후자까지 "검토 중"이면 **누가 무엇을 하고 있는지 화면에서 구분되지 않습니다.** AI는 분석하고 사람은 검토한다 — 이 구분이 기획서 4장 책임 경계를 화면에서 지탱합니다.

이 규칙은 **보안 담당자용 SCR-02에만** 적용합니다. 직원용 SCR-01의 스피너 문구 "보안 검토 중"과 실패 안내 "자동 검토 실패 — 담당자 확인 중"은 기획서 5.3이 고정한 **프로세스 안내 문장**이며 그대로 둡니다. 직원에게는 자기 프롬프트가 보안 검토를 받고 있다는 사실만 필요하고, AI가 개입했는지는 직원의 관심사가 아닙니다. 값 라벨은 행위 주체를 구분하고, 안내 문장은 기획서 문구를 따릅니다.

## 2. SCR-01 직원 AI 챗

레이아웃 골격은 기획서 5.3의 ASCII 도해를 따릅니다. 아래는 그 도해가 정하지 않은 것만 채웁니다.

### 2.1 컴포넌트와 데이터 소스

| 컴포넌트 | 역할 | 데이터 소스 (필드 경로) |
|---|---|---|
| `AppHeader` | 서비스명, 탭, 계정 전환 | GET `/users` → `items[].{userId,name,department}` |
| `PolicyCaption` | 하단 캡션 "부서: 개발팀 · 적용 정책 N건" | GET `/policies?deptId=` → 반환 정책 배열 길이 |
| `MessageInput` | textarea 3줄 + 전송 버튼 | 로컬 상태. 전송 중 비활성 |
| `MessageBubble` | 직원 발화. **사용자가 방금 입력한 로컬 텍스트**를 표시 (D15). 마스킹된 경우 `submittedText`의 `[라벨]`을 하이라이트해 무엇이 치환됐는지 보여줌 | 발화 본문 = FE 로컬 상태 / 하이라이트 대상 = POST `/messages` → `submittedText` |
| `VerdictCard` | 판정 결과 카드 | POST `/messages` → `decision`, `status`, `ruleResult.matches[]`, `policySnapshot.policies[]` |
| `PendingIndicator` | 스피너 + "보안 검토 중" + 경과 시간 | 폴링 로컬 상태 + `aiStatus` |
| `AiCandidateList` | AI 후보 목록 (읽기 전용) | GET `/inspections/{id}` → `aiAssessment.riskCandidates[].{code,category,rationale,evidence[]}` |

`VerdictCard` 내부 행 하나는 `ruleResult.matches[i]`의 `code` · `category` · `action` · `source`로 구성하며, `embargoUntil`이 있으면 "YYYY-MM-DD 해제" 칩을 덧붙입니다. 판정이 BLOCK이고 엠바고 매칭이 있으면 카드 하단 힌트가 "○○부터 공개할 수 있는 내용입니다"로 바뀝니다 — 언제 다시 시도하면 되는지 모르면 사용자는 우회를 학습합니다 (0.5 D20). 카드 헤더의 "규칙 N건"은 **`matches` 배열 길이**이며 `appliedRuleCodes` 길이가 아닙니다 — 적용된 규칙과 매칭된 규칙은 다릅니다 (8.4, D1).

### 2.2 5개 상태 프레임

| 프레임 | 트리거 | 필수 표시 요소 | 배지 |
|---|---|---|---|
| **S1 초기** | 진입 | 빈 대화 영역(안내 문구 1줄), 입력창 활성, PolicyCaption | 없음 |
| **S2 허용** | 200 · `decision=ALLOW` | 발화 원문 그대로, "규칙 0건", 판정 카드는 1줄로 축약 | 허용 (`green`) |
| **S3 마스킹** | 200 · `decision=MASK` | 마스킹본(`[전화번호]` 하이라이트), 적용 규칙 목록, "마스킹 후 전송됨" | 마스킹 (`amber`) |
| **S4 차단** | 403 · `decision=BLOCK` | **발화 버블에 입력 원문 표시**(D15), 적용 규칙 목록 + 의무/출처, "수정 후 재전송" 안내, **입력창에 원문 복원** | 차단 (`red`) |
| **S5 검토 대기** | 202 → 폴링 | (a) 폴링 중: 스피너 + "보안 검토 중" + 경과 초 (b) 완료 후: "검토 대기 (담당자 확정 필요)" + AI 후보 목록 읽기 전용. 두 문구 모두 기획서 5.3이 고정한 프로세스 안내이며 SCR-02의 `aiStatus` 라벨과 다른 계열이다 (1.3) | 검토 대기 (`purple`) |

S5는 한 프레임 안에 (a)(b) 두 상태를 나란히 배치하거나 프레임을 S5-a / S5-b로 나눕니다. 데모에서 Mock 지연 2.5초 동안 (a)가 실제로 보입니다 (9.5).

S4에서 규칙 행의 오른쪽에는 의무를 표기합니다 — `obligation`이 LEGAL이면 "법령", INTERNAL이면 "사규". `source` 문자열은 규칙에 저장된 값을 그대로 출력하며, **법령 조문 번호를 화면 문구로 단정하지 않습니다** (7.2 하단 주석).

### 2.3 상태 전이

```
S1 초기
 ├─ 전송 → 200 decision=ALLOW ──────────→ S2 허용 ─┐
 ├─ 전송 → 200 decision=MASK ───────────→ S3 마스킹 ┤→ 입력창 비움 → S1
 ├─ 전송 → 403 decision=BLOCK ──────────→ S4 차단 ──→ 입력창에 원문 복원 → (수정) → 전송
 └─ 전송 → 202 decision=PENDING ────────→ S5-a 폴링 중
                                            ├─ aiStatus=COMPLETED → S5-b 검토 대기 + AI 후보
                                            ├─ aiStatus=FAILED ───→ S5-b' "자동 검토 실패, 담당자 확인 중"
                                            └─ 30회 초과 ─────────→ "잠시 후 다시 확인"
S5-b ──(담당자가 SCR-02에서 확정)──→ 화면 새로고침 → 차단 또는 허용 배지
```

마지막 전이는 폴링이 아니라 **새로고침**입니다. 폴링은 `aiStatus` 기준으로만 종료하며, 사람의 확정 시점은 예측할 수 없어 폴링으로 따라가면 무한 폴링이 됩니다 (5.3, D12). 데모 조작도 새로고침입니다.

| 1 | 전송 클릭 → 입력창·버튼 비활성 → 응답 수신 후 활성 | 5.3 |

## 3. SCR-02 관리자 감사 콘솔

레이아웃 골격은 기획서 5.4의 ASCII 도해를 따릅니다.

### 3.1 필터 바

| 필터 | 파라미터 | 옵션 | 비고 |
|---|---|---|---|
| 부서 | `deptId` | 전체 / 개발팀 / 영업팀 / 인사팀 | **정보보안팀 없음** (D2) |
| 상태 | `status` | 전체 / 허용 / 마스킹 / 차단 / 검토 대기 | 값은 ALLOWED·MASKED·BLOCKED·PENDING_REVIEW, 표기는 5.6 |
| 기간 | `from`, `to` | 기본 최근 7일 | 시드 로그가 과거 7일 분포 (10.5) |
| 총 건수 | — | `total` | GET `/inspections` → `total` |

우측 상단 "총 N건"은 응답의 `total`을 그대로 씁니다. 기획서 5.4 도해의 "137건"은 예시 숫자이며 실제 화면은 시드 로그 + 데모 생성분입니다.

### 3.2 목록 컬럼

| 컬럼 | 필드 경로 | 표시 규칙 |
|---|---|---|
| 시각 | `items[].createdAt` | `MM-DD HH:mm` |
| 부서 | `items[].department` | 텍스트 |
| 사용자 | `items[].userName` | 시드가 이미 `김OO` 형식. 추가 마스킹 없음 |
| 판정 | `items[].status` | 배지 (1.2 표) |
| 규칙 수 | `items[].ruleCount` | `source=RULE`인 finding 수 |

| 확정 | `items[].decidedBy` | RULE / HUMAN / `—` (D10) |

페이지 크기 20, `page`는 0부터 (8.4).

### 3.3 상세 패널 4개 섹션

행 클릭 → GET `/inspections/{id}`.

| # | 섹션 | 표시 내용 | 필드 경로 |
|---|---|---|---|
| 1 | 원문 | 마스킹된 본문만. 원문 열람은 Future. `submittedText`가 비는 경우는 **규칙 BLOCK 한 가지뿐**이며(마스킹본이 생성된 적 없음), 사람이 ACCEPT로 차단한 건은 본문이 그대로 남는다 — ACCEPT 후에도 패널에서 본문이 사라지지 않아야 한다 (D14) | `submittedText` |
| 2 | 규칙 판정 (결정) | 규칙 코드 · 카테고리 · 액션 · 의무 · 출처. 제목 옆에 "결정" 꼬리표 | `findings[]` where `source=RULE`, `ruleResult.matches[]` |
| 3 | AI 제안 (후보) | 후보 코드 · 근거(rationale) · 출처(evidence) · 검토 상태 배지 | `findings[]` where `source=AI`, `aiAssessment.riskCandidates[]` |
| 4 | 이력 | 정책 버전, 확정 주체, 확정자, 확정 시각 | `policySnapshot.policies[]`, `decidedBy`, `findings[].reviewedBy`, `findings[].reviewedAt` |

섹션 2와 3은 **좌우 또는 상하로 시각적으로 분리**하고, 2에는 "결정", 3에는 "후보" 꼬리표를 붙입니다. 이 분리가 기획서 4장 책임 경계를 화면으로 증명하는 장치입니다.

### 3.4 ACCEPT / REJECT 버튼 노출 규칙

| finding | `source` | `reviewStatus` | 버튼 |
|---|---|---|---|
| AI 후보, 미검토 | AI | SUGGESTED | **[ACCEPT] [REJECT] 노출** |
| AI 후보, 확정됨 | AI | ACCEPTED | 노출 안 함. 배지 "확정(위반)" |
| AI 후보, 기각됨 | AI | REJECTED | 노출 안 함. 배지 "기각" |
| 규칙 판정 | RULE | CONFIRMED | **노출 안 함.** 배지는 "확정(규칙)" (`blue`) |

규칙 finding에 버튼을 노출하면 "AI 후보만 사람이 확정한다"는 책임 경계(4장)와 정면으로 어긋납니다 (D6). 버튼 미노출은 UI 방어이고 서버 검증이 최종 방어입니다 — CONFIRMED인 규칙 finding에 PATCH가 도달해도 서버는 **409**를 반환하며, 이미 처리된 AI 후보의 재요청과는 에러 코드로 구분합니다 (D13, 8.4).
